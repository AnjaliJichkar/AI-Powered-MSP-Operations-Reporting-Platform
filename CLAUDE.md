# CLAUDE.md — Inputiv Engine

This repository is the shared engine behind three Inputiv products: **Desk** (internal cross-tool agent), **Resolved** (AI triage + guaranteed human resolution), and **Memory** (resolution knowledge base). Read `docs/CONTEXT.md` for the business background and `docs/inputiv-development-plan-v2.md` for the roadmap. This file is the set of rules you follow on every task.

## What we are building right now (Phase 1: Desk)

A read-only agent that answers plain-English questions across an MSP's tool stack. Inputiv engineers ask it questions in Slack; it calls tools over our connectors and returns an answer.

It is no longer internal-only. Franchisees sign in to their own client: an admin can ask questions about their own estate and read their own audit trail, a viewer reads the reviews we have released to them, and neither can see another franchisee's anything. See "Authentication and authorization".

**Build order for Phase 1 (do not reorder without asking):**
1. FastAPI skeleton, database models, migrations, settings.
2. Connector base class and the NinjaOne connector as the worked example.
3. `/chat` endpoint with the Claude tool-call loop, exposed via a Slack bot.
4. Autotask connector.
5. **Demo freeze: October 2, 2026.** Everything above must work on real data for one pilot franchisee by then.
6. Bitdefender, N-able Cove, ConnectSecure, Blackpoint connectors (after the freeze).
7. Hardening: rate limits, token refresh under concurrency, pagination edge cases, safety tests.

## Hard rules

These are not preferences. If a task seems to require breaking one, stop and ask.

1. **Every tool call is scoped to a client, and within it to a site.** Every tool function takes `client_id` as a required parameter and an optional `site_id`. Both are resolved server-side; the model never sees, chooses, or passes either, nor any credential. A request without `client_id` fails. A `site_id` that does not belong to the current client fails before any API call. Records returned by a vendor are checked against that client's allowlist of vendor IDs, never against a single ID.
   **The client is resolved from the session, never from the request.** No endpoint takes a `client_id` or a `user_id` in a body or a query string; the request models forbid unknown fields, so a caller that sends one is told rather than ignored. See "Authentication and authorization".
2. **Read-only by default.** No tool creates, updates, or deletes anything in any external system, and every connector stays read-only everywhere else. When write access arrives, the only write path will be the automation engine (`app/automation/`, see "Automation"): fixed, versioned workflows written in code, executed through write clients that nothing else uses, behind a per-client switch, a dry run, a two-person approval and an audit row for every step. Nothing has write access yet.
3. **No secrets in code or fixtures.** API keys, tokens, and passwords come from environment variables or the secrets manager. Recorded fixtures are scrubbed before commit.
4. **Every prompt, tool call, and result is logged** to `audit_log` with the user, client, timestamp, and outcome. **A failure is logged on a connection of its own** (`audited_read`): a failed vendor read is usually the last thing to happen in its caller's transaction, so a row written inside that transaction goes when it rolls back and the run that failed leaves nothing behind — which is how a live 500 came to be absent from the record entirely. Audit may not fail a run either: if the row cannot be written, the caller is still told what the vendor said and the write's own failure is logged.
5. **One connector layer.** All products call the same connectors. Never build a product-specific integration.
6. **Cap and time-limit every agent run.** Maximum tool calls per request and per-call timeouts are configuration, not constants in code.
7. **Never fabricate data.** If an API returns nothing or errors, the answer says so. The model does not guess device names, ticket numbers, or statuses.

## Stack

- Python 3.12, FastAPI, SQLAlchemy 2.x (async), Alembic, Pydantic v2, `pydantic-settings` for config, `httpx` (async), `pytest` + `pytest-asyncio`, `respx` for HTTP mocking.
- PostgreSQL, via the `asyncpg` driver. `uvicorn` runs the app.
- `cryptography` (Fernet) encrypts `ToolCredential` secrets at rest, and the TOTP secrets beside them. Keys come from env and are handled only in `app/security/crypto.py`.
- `argon2-cffi` hashes passwords (argon2id), and nothing else does. A memory-hard KDF is not something to write by hand. One-time codes are RFC 6238 over the standard library's `hmac`, because that algorithm is fully specified and a dependency would buy nothing.
- Anthropic Python SDK for the agent loop. Model name is a setting, not a constant.
- Slack Bolt for the Phase 1 interface.
- `python-pptx` renders the review deck and `reportlab` the Monthly Report PDF: both pure Python wheels, so a render needs no system package on Render's native runtime. Nothing else writes a document.
- `tzdata` carries the IANA time zone database, because Windows ships none and `zoneinfo` cannot load `America/Chicago` without it: the SLA clock would run in UTC on a developer's machine and correctly on Linux, which is the worst of both.
- `ruff` for lint and format; `mypy` in strict mode on `app/`.

## Connector pattern

Every connector follows `app/connectors/ninjaone/` exactly. When adding one, copy the NinjaOne structure and change the specifics.

- `client.py`: an async class extending `BaseConnector`. Handles auth and token refresh, pagination, retry with exponential backoff on 429/5xx, and raises `ConnectorError` subclasses (`AuthError`, `RateLimited`, `NotFound`, `UpstreamError`). It receives credentials in its constructor; it never reads them from env itself.
- `models.py`: Pydantic models for the API responses we actually use. Do not model the whole API.
- `tools.py`: functions decorated with `@tool` from `app/agent/registry.py`. Each has a docstring that becomes the tool description the model sees, typed parameters, a required `client_id: str`, and returns a Pydantic model or list. Keep tools narrow: `list_devices_not_checked_in(client_id, days)` rather than `query_devices(client_id, filter)`.
- Tests: `respx` against fixtures in `tests/fixtures/<connector>/`. Every tool has at least one happy-path test and one error test (401, 429, empty result).
- Results are compact. A list tool returns only the fields the prompt needs per row (`app/connectors/results.py`: `SiteTagged` rows, a `RowCapped` result), never more than its row cap (`@tool(max_rows=...)`, default `TOOL_MAX_ROWS`, applied with `capped()` after sorting), and always `total`, `returned`, `truncated` and a `truncation_note`. Offer filters (class, OS, status label, priority label, age, assignee, site) and count tools (`count_devices`, `count_tickets`) so "how many" is one small call, never a dump the model counts. A tool whose rows carry only a `deviceId` (NinjaOne `/v2/queries/*`, alerts, activities) resolves them through the inventory's `deviceId → organizationId` map (`place_by_device`) before the allowlist guard; it never trusts a row it cannot place. Send a vendor filter only from a fixed map of values we have seen it honour, in the vendor's exact spelling, and apply it again on our side: NinjaOne's install history silently ignores an unknown `status` and returns everything, while its waiting list returns zero rows for one (and for the right value in the wrong case) — opposite failures, neither an error. An unknown value raises a `ValueError` naming the accepted ones before any request (`_vendor_value`); the loop hands a tool's `ValueError` back to the model as a correctable error, so write those messages for the model. GravityZone does the opposite: an unknown value is a -32602 error naming the accepted values, which `BitdefenderClient` returns as `ArgumentRejected` (also a `ValueError`) so the model can correct it, while -32602 with "does not exist" or "do not have full access to" is `NotFound`; its silent cases are a company read without `depth.allItemsRecursively` (0 rows) and incidents without an EDR licence (empty), both handled in code. ConnectSecure is the worst of the four and never raises: an unknown field or value empties a `/r/company/*` or `/r/asset/*` read and is ignored by a `/r/report_queries/*` one, so NinjaOne's two directions are its rule, split by endpoint family. When a filtered list still runs to thousands (`list_patch_installs`, `list_patch_status`), return totals computed before the cap beside the capped rows. The selection check on real engineer questions must stay at or above 90%; the tool count is monitored, not capped (51 today: 16 NinjaOne, 14 Autotask, 5 Bitdefender, 5 ConnectSecure, 5 Microsoft 365, 3 Cove, 2 coverage registered under NinjaOne and 1 backup coverage registered under Cove — a gap is the board's join whoever asks for it, so it lives with the board). Run `scripts/selection_check.py` before and after adding or removing a tool, record both results in `docs/validation-log.md`, and update the pinned count, which is in two files (`tests/connectors/test_autotask_reports.py` and `tests/connectors/test_bitdefender.py`; each names the other); a change that takes selection below 90% is not merged until descriptions, the prompt's question map or the tool set are fixed. Data only a report needs is a connector client method, not a model tool (NinjaOne `list_locations`); extend an existing tool with a filter rather than adding a near-duplicate. Every tool description ends by saying what the tool is NOT for and naming the tool that is (`tests/agent/test_registry.py` enforces it), so overlapping tools stay distinguishable.

- **A vendor that counts conditions is counted against in the query builder, not in the caller.** Autotask expands every `in` filter into one OR condition per value, caps a query at 500 of them and reports breaching it as an HTTP **500** with no message (api-notes, live 2026-10-01: 544 refused, 401 accepted the same minute). The limit is on the whole filter, and no caller knows the whole filter — the one that broke knew its own 400 ticket ids and nothing about the 144 companies the client scope was about to AND onto them, a number decided by how many customers the franchisee has. So `_query_all` counts every clause (`_conditions`) and splits the widest `in` list until each query is under `AUTOTASK_MAX_FILTER_CONDITIONS` (450, under the vendor's 500 so an unforeseen clause has somewhere to go), with every other clause riding along unchanged on each part so the answers concatenate; a filter whose unsplittable clauses already fill the budget raises a `ValueError` before any request, which the loop hands back to the model as correctable. `MAX_IN_CLAUSE_VALUES` stays what it was: the cap on one caller's own list, past which that caller reports its answer truncated. A later vendor with a counted limit does the same in its own builder.
- `sync_sites` never puts two organisations of one connector on one site by name alone. A new organisation is matched by a name a merge left the site remembering; else by name to a site not yet on this connector; else by **device overlap** — its hostnames (`hostnames_by_organisation()`, a raw tenant read for sync only, names kept in memory) against the hostnames the client's other tools hold per site, mapped onto that site at or above `SYNC_OVERLAP_SHARE` and reported "linked by device overlap"; below it, or named like a site already on this connector, it is created and listed under "possible duplicates". GravityZone's six-character integration suffix is stripped before matching (`naming.vendor_match_key`). A mapped organisation the vendor stops returning is reported "mapping no longer found" and left in place for a person; the site is deactivated only when nothing stands for it on any connector. The sync output and the Coverage board both list "vendor duplication": sites holding more than one organisation on a connector, with names, ids and counts, for the franchisee to consolidate at the vendor.
- `sync_sites`: every connector implements `list_organisations()`, returning the tenant's *customer* organisations (Autotask: `companyType` resolving to "Customer" via the tenant's picklist, `isActive`, and never company 0). `app/connectors/sync.py` turns that into `Site` rows and site-level `ToolMapping` rows. It matches a second connector's organisation to an existing site by `Site.normalized_name` (`normalise_name` in `app/models/site.py`) rather than creating a duplicate; records the franchisee's own internal organisations inactive, by per-client rules in the tenant-level mapping's `extra["sync"]` (`app/connectors/naming.py`; set with `manage_client.py sync-rules`); adopts a tenant-level mapping that already carries the vendor id; aborts with `SyncConflict` if another client holds it; and marks sites the vendor no longer lists inactive. Run it from `scripts/sync_sites.py` after adding credentials, and again whenever the franchisee onboards a customer. `scripts/link_sites.py` merges or deactivates sites the matching got wrong.

- **A vendor that cannot scope a key read-only gets an allowlist in code.** GravityZone API keys can start scans and move endpoints with the same key that lists them, so `BitdefenderClient` holds `READ_ONLY_METHODS` (read methods per JSON-RPC service), checks every call against it before a request is built, and raises `ReadOnlyViolation` for anything else with no HTTP made. `validate_connector.py --check-bitdefender` proves it on every pre-flight. A later connector with the same problem does the same; hard rule 2 is enforced in our code, not trusted to the vendor. The allowlist holds only methods with a live fixture; a method whose parameter shape could not be determined is removed and listed in the api-notes as a candidate. Keys are requested least-privilege (the five APIs in `USED_APIS`), and the pre-flight warns, naming each one, when a key can call more.
- **ConnectSecure's key is a user, and its role is the write surface.** `ConnectSecureClient` sends exactly two kinds of request: `POST /w/authorize` and `GET`s to `READ_ONLY_PATHS` (exact `/r/` paths; a write, a delete, an unlisted read or a read path with the wrong verb raises `ReadOnlyViolation` before any HTTP). Its pre-flight (`validate_connector.py --check-connectsecure`) reads the key's own user and warns, naming the role, when it is not a viewer; the pilot's key is an ADMIN, so it warns every run. Companies are sites; a site read sends `company_id` in the endpoint's `condition` and the allowlist guard checks every row anyway. Every vulnerability count carries the scan dates it came from. The risk score runs 0 to 100 and higher is worse, as Bitdefender's does.
- **ConnectSecure reports every finding twice: confirmed and suspected, and they are never added together.** The scanner *confirms* a finding when it proved the vulnerable build is on the machine and *suspects* one it inferred from a version number; both views return both by default and they differ by more than half (live: 3,869 confirmed of 8,278). `unconfirmed=false` narrows both the findings and the remediation view and reconciles exactly with `asset_view`'s per-asset counters, which are the confirmed population and what the vendor's own console shows. Every tool defaults to `include_unconfirmed=False` and returns a `population` string saying which set it counted; every review number is confirmed-only, with one caveat fact for the rest. A finding row carries no fix and no known-exploited flag of its own: a fix is joined from the remediation view **by asset id and normalised product, never hostname** (an unmatched join reads "fix not reported"), and known-exploited comes from `asset_view.cisa_vul`, with problem group 34 read only to list the KEV CVEs themselves.
- **ConnectSecure's companies sync leaves unmapped are known to the guard.** `list_organisations()` skips deleted and assessment companies, so they never become sites, and a tenant-wide listing still returns their rows. On the first row it cannot place, the client reads the company list once per client (`_load_known_excluded`, kept for the inventory's TTL) and drops rows from `deleted` and `assessment` companies at INFO with their ids, a live company nobody synced (`unsynced`) and an id the tenant does not list at ERROR with theirs; never a name. Live, 2026-09-28: the 16 asset rows and 17 agent rows dropped on every board were all one live company no site holds (`unsynced`), which stays at ERROR until `sync_sites` is run for it (validation log).
- **ConnectSecure's `condition` filter fails silently in both directions.** One grammar live, `field=value` with strings quoted; an unknown field or value returns zero rows on `/r/company/*` and `/r/asset/*` and is ignored, returning everything, on `/r/report_queries/*`. So a condition is built only by `build_condition` from `FILTER_FIELDS` (a fixed map per path, strings always quoted), and every filter is applied again on our side, a failing row raising. `skip` is a record offset but the report views have no stable order across reads, so a listing is read as one page sized to the vendor's `total`, capped by `CONNECTSECURE_MAX_ROWS` and reported `truncated` beyond it, never silently partial. The vendor sends no quota headers, so `ledger.py` counts requests per tenant per UTC day against the 30,000 limit, warns at half, four fifths and the whole, and the pre-flight prints the day's count.
- **A Bitdefender module has four states, decided with the licence.** `getLicenseInfo` is read once per site; a module is `enabled`, `disabled` (licensed, off by policy), `not_licensed` (the licence's `manage*` flag is false, whatever the row says) or `not_reported` (absent from the row). The module list comes from the rows (`modules_seen`), never a fixed tuple: the live map has 16 keys, seven of them undocumented, and seven documented ones never appear. `count_endpoints(group_by='module')` reports only modules the tenant has; `edr_licensed` per site decides whether detections can exist at all, so `list_recent_detections` says "EDR is not licensed" rather than returning an empty week.
- **Cross-tool device matching** is by normalised hostname (lower case, domain suffix stripped) and only within a site (`app/connectors/matching.py`). Nothing fuzzier: a near miss must show as two unmatched devices, never as a wrong pair.

Credential resolution: `ToolCredential` rows are keyed by `(client_id, connector_name)` and encrypted at rest. `app/connectors/factory.py` builds a connector instance for a given `(client_id, connector_name, site_id?)`; nothing else constructs connectors.

## Tenancy

Two levels, and the distinction matters for every query.

- **Client** is the franchisee — the MSP we work for. It owns the credentials. `client_id` is a UUID and is the top-level scope of every call.
- **Site** is one of that franchisee's own end customers. It is what the vendor calls an organisation (NinjaOne) or a company (Autotask). Sites are discovered by `sync_sites`, never typed in, and are deactivated rather than deleted when the vendor stops listing them.

`ToolMapping` rows come in two kinds, told apart by `site_id`:

- `site_id` set: the vendor's organisation or company ID for one end customer. This is what scopes a data read. Unique per `(connector_name, external_id)` across every client, so two franchisees can never resolve to the same organisation. **A site may hold more than one per connector** (since migration 0013): a customer with a hand-made GravityZone company and an integration-created one holds both, the scope carries one `SiteRef` per mapping, a site-scoped call fans out over all of them and merges, the guard accepts any of them as that site's, and "one site" everywhere means one distinct `site_id`, never one ref (`sites_covered` is `scope.target_slugs`, a site once). **Every per-organisation read goes through `BaseConnector._fan_out_refs`**: when the vendor no longer knows one of a site's organisations (`NotFound`, or an `ArgumentRejected` on the id itself) and another organisation of the same site answered, the read goes on from the other and logs which was spared; a site whose only organisation is gone, or any other failure, raises as before, so a partial read is never passed off as a whole one. Live, 2026-09-25: a merged site's hand-made company had been removed at GravityZone since the merge, `parentId` was refused for it, and every site-scoped Bitdefender read for that site failed until this. The sync reports such a mapping as "no longer found" and leaves it for a person. Site-level readers that take one company by design — the Autotask company card and the review's company facts — read `get_site_companies(site_id)` and count contracts across all of them (`count_site_active_contracts`); Bitdefender detections are asked only of the companies whose own licence has EDR (`companies_with_edr`), the site's union deciding only whether detections can exist at all. `link_sites.py --merge` combines two sites' mappings on one connector rather than refusing; the one refusal left is two organisations in different vendor tenants (`TENANT_KEYS` in `extra`). The kept site remembers the names it absorbed (`Site.absorbed_names`) so the next sync maps them back to it.
- `site_id` NULL: tenant-level, for the franchisee as a whole. At most one per `(client_id, connector_name)`. It carries per-client configuration in `extra` and never a vendor id (`external_id` is nullable; a check constraint forbids it on tenant-level rows). It never scopes a data read. Rows from before sites existed still carry one until `sync_sites` adopts them onto their site.

How a call is scoped:

- **With a site.** The engine verifies the site belongs to the current client before any API call, then queries that site's vendor ID alone.
- **Without a site.** The connector runs across the client's active sites and merges the results, tagging every record with the site it came from. An answer that spans sites must say which row belongs to where.

`_scoped()` checks returned records against the client's **full allowlist** of vendor IDs, not the single ID being queried. A sibling site appearing in a response is a filter bug and is dropped with a warning; a record from one of the client's *inactive* sites (`ClientScope.excluded`) is dropped quietly; a record from an organisation we have no site for is dropped with an error and can never be merged in. That last case is what makes a tenant-wide listing (NinjaOne `GET /v2/devices`, used when no site is named) safe: it is classified row by row, never trusted.

Anything cached from a vendor is keyed by the scope it was fetched under, never by client alone. NinjaOne's `InventoryCache` keys an entry by `(client, the sites the fetching call targeted)` and serves a later call only when the entry covers every site that call targets: a whole-client inventory may serve a named site (narrowed on read), a site-scoped one never serves an unscoped question. A new cache follows the same rule.

Requests to a vendor are shared within a process, because the factory builds a connector per tool call and the loop runs a model's parallel tool calls together. Three rules, each from a live finding (docs/api-notes/ninjaone.md):

- **One token per client, not per connector.** NinjaOne access tokens live in `app/connectors/ninjaone/tokens.py`, keyed by client and credential version (plus host and OAuth scope), behind one shared lock. Never shared across clients; a connector with no credential version keeps its token to itself; a 401 discards only the rejected token. Memory only, never logged. A new token-based connector does the same.
- **Concurrent cache misses are single-flighted** (`InventoryCache.flight`): one fetches, the rest wait and re-check.
- **Only an unscoped call touches the tenant inventory.** A site-scoped call places `deviceId` rows through that site's own device listing; a `deviceId` it does not hold is out of scope and dropped (warning). Unscoped, an unknown `deviceId` is an error.
- **A `/v2/queries/*` cursor is a server-side position** and the same name is sent on every page after the first; `query()` checks the envelope's `offset` against the rows already read on every page and raises on a cursor that restarted (rows would repeat) or skipped (a retry advanced it), logging each page at DEBUG (api-notes/ninjaone.md).

The model names a site by **slug**. The system prompt carries the client's site list as names and slugs only — never IDs. The loop resolves the slug to a `site_id` within the current client and rejects a slug outside it.

## Authentication and authorization

Phase 1 had no identity: an engineer typed a handle and the engine believed it, and any caller could name any client. Both are gone. Who is calling comes from a session cookie, and which tenant they are on comes from the session row.

**Two tenancy axes, deliberately separate.** A `Client` is a franchisee we hold credentials for; an `Organisation` is a set of people who sign in. Exactly one organisation is Inputiv's; every other is bound to one client. A franchisee is onboarded, synced and reported on before anyone from it has an account, and deactivating a client's logins is not the same act as deactivating the client.

**Five roles**, and the role names its organisation kind (a check constraint on `users` enforces the pairing, as well as the resolver):

- `inputiv_admin` — everything, including organisations, users and invites.
- `inputiv_engineer` — chat, threads, reviews and the review screen, on whichever client they have switched to. Not account administration.
- `franchisee_admin` — their own client only: chat, their own threads, their own audit trail, invites into their own organisation, and **making the business reviews of their own customers** — generating one, settling the findings held for somebody who knows the estate, approving the Monthly Report, and rendering the client copy, which releases it. Not the workings (see "What a franchisee sees of a review").
- `franchisee_technician` — the people who fix things, on their own client: Ask, the device pages, the coverage board including Refresh and exclusions, and the ticket workspace. No accounts, no approving or releasing a review; reviews are read exactly as a viewer reads them. It is in `CAN_RUN_MODEL` with the administrator, which is what gives it Ask, tickets and the coverage actions, and out of `INVITE_ADMIN` and `audit-read`, which is what keeps the account and the record away from it (migration 0021).
- `franchisee_viewer` — released reviews, and nothing that runs a model.

**Scope is (organisation, optional site).** The site half is carried everywhere and used nowhere yet: no user is pinned to a site. It is modelled now because retrofitting a second axis after every route and test assumes one is the kind of change that gets done incompletely.

**One resolver, and every route declares against it** (`app/auth/dependencies.py`). A route says what it needs — `Depends(CAN_CHAT)`, `Depends(INPUTIV_ANY)`, `Depends(PUBLIC)` — and gets a resolved `Scope` or no response. The check is that every route declared *something*, not that every route is protected: `undeclared_routes` enumerates the application, `create_app` refuses to build with any, and `tests/api/test_scope_declarations.py` asserts the same and proves the enumeration is not vacuous. A route added without a declaration is a server that does not start, not a quiet hole. Two declarations on one route are refused as well: which would win depends on ordering nobody should have to reason about.

The resolver, in order, stopping at the first refusal: the session from the cookie; a suspended user or organisation refused as an expired session; the CSRF token on anything that changes state; the role against the ones the route named; then the client — a franchisee user's own, or the one an Inputiv session was switched to. **`client_id` is an output of this function, never an input.** Inputiv staff acquire a client only through `POST /auth/switch-client`, which writes a `client_switched` audit row naming both clients every time, so which tenant we were working on is a row somebody can read.

**Sessions are rows; the cookie holds a random token and nothing else.** No identity, no role, no client, no expiry a client could edit, so revoking a session is a write that takes effect on the next request. The cookie is `HttpOnly`, `Secure` and `SameSite=Lax`; settings refuse a non-Secure cookie anywhere but `ENVIRONMENT=local`. Two expiries are checked on every request: absolute, set at sign-in and never extended, and idle. `last_seen_at` is written only when it has drifted past `TOUCH_INTERVAL_SECONDS`, so an active session is not a write per request. The database holds a SHA-256 of the token, so a leaked table yields nothing replayable — a plain hash and not argon2, because this is 256 bits of our own randomness rather than something anyone can guess.

**CSRF is a synchroniser token.** The session row holds one, `GET /auth/me` hands it to the page, and every `POST`, `PUT`, `PATCH` and `DELETE` must send it in `X-CSRF-Token`. It is stored in the clear on purpose: it is handed back on every page load and is worthless without the cookie, which script cannot read.

**Two throttles, different in kind, and both needed.** The lockout (`LOGIN_MAX_FAILURES`, `LOGIN_LOCKOUT_MINUTES`) is a column, so it survives a restart and follows the account wherever it is attacked from. The rate limit (`LOGIN_RATE_LIMIT_PER_MINUTE`) is per client address and in memory, so it sees a spray across many accounts that no per-account counter could — and being in memory it is per process, which is written down rather than hidden: put a limit in the proxy as well when the engine runs more than one worker.

**A refused sign-in says one thing, whatever the reason.** An unknown address, a wrong password, an invited account and a suspended one all take the same work (`verify_password` hashes against a throwaway when there is no stored hash) and give the same message, so the endpoint cannot be used to find out who has an account. The reason is in the audit row, where it belongs. Status is checked only *after* the password is known to be right, so a wrong password never reveals that an account is suspended.

**A second factor is optional per user** and required at sign-in only once the user has proved a code, so an abandoned enrolment never locks anybody out. **Outside `local` it is not optional for Inputiv staff**: `TOTP_REQUIRED_FOR_INPUTIV` must be true (settings refuse to start otherwise), and a staff account without a confirmed code signs in, sees itself, can enrol on Settings, and is refused everything else with `403` and `X-Second-Factor: enrol` (`ScopeRule.second_factor_exempt` marks the few routes enrolment needs; `SIGNED_IN` is the only one). Franchisee accounts are not held to it. The same start-up check refuses `DEBUG`, `DATABASE_ECHO`, and a `PUBLIC_BASE_URL` or `DATABASE_URL` on the local machine, beside the older refusals of an http link and a non-Secure cookie: a laptop option cannot reach production by omission (`docs/deploy.md`, step 3). The secret is returned exactly once, at enrolment, and stored encrypted with the credential cipher. Turning it off, or changing a password, ends every session the account holds.

**Passwords are argon2id** and nothing else hashes one. Cost is configuration, not a constant: a stored hash carries the parameters it was made with, and `verify_password` reports when it should be upgraded so the next successful sign-in writes back a stronger one. The only rule is length; complexity rules push people towards predictable substitutions and a second place to write the result down.

**The actor is the authenticated user.** `audit_log.actor_user_id` and `conversations.owner_user_id` are the account, `actor_id` is its id as text, and both foreign keys are `ON DELETE RESTRICT` for the same reason `audit_log.conversation_id` is. **Rows written before sign-in existed keep the handle they already hold** and were not rewritten by the migration: hard rule 4 says the record is append-only, and reassigning old rows to accounts that did not exist at the time would be a lie about the past. A thread started before sign-in cannot be opened through the API at all — `check_access` refuses it rather than comparing a handle against a user id. The CLI scripts are not authenticated and still attribute to an operator handle with no account; they need database credentials, which is the boundary they rely on.

**What a franchisee sees of a review, and what their administrator may do to one.** Three audiences, not two, and the two axes are deliberately separate: **who may act** is `CAN_MAKE_REVIEWS` (Inputiv staff and `franchisee_admin`) and **who may look behind the words** is `Scope.sees_drafts` (Inputiv staff alone).

Inputiv staff see a review while it is being made: drafts, held findings with their sources and fact ids, the fact-id trace under every sentence, and the `internal` and `demo` render modes. A technician or a viewer sees one only once it is *released* — status `rendered` with a `client` deck rendered from exactly its current content — and then only the deck's words. "Released" is not a fourth status: rendering in client mode is the act of releasing, and any change to a review empties `renders` (and the name of whoever released it), so a released review cannot drift from the deck that was released.

**A franchisee's own administrator makes the reviews of their own customers.** They generate one, confirm or dismiss the findings held for somebody who knows the estate, approve the Monthly Report, and render the client deck and PDF — which is the act of releasing. The person who presents the review to the customer is the person who decides when the customer has it. What stays ours is everything that shows how it was made or writes what it says: the fact-id trace, every fact and its definition, the collection gaps, a finding's raw `sources` and `fact_ids`, whether a sentence was drafted by the model or fell back to code, the `internal` and `demo` renders of either output, and the drafting actions (`add`, `edit`, `remove`, `scores`, `notes`, `contact_names`, `industry`). **Industry Trends is the one approval they do not have**, because a trend is web-research output on a customer's deck and an engineer signs it; the Monthly Report's approval is theirs, because without it they could release a deck and never a PDF of a review they made themselves.

`_admin_view` is that third shape and is **built from the parts a review is made of, as `_released_view` is**, rather than the internal view with fields removed: a field added to the document later does not leak by default, it has to be added. A finding's tools reach them as vendor *names* computed on the server (`_finding_tools`), never as keys, because a key a reader may not see is not one to send and then not draw. An unreleased review is still a 404 to a technician and a viewer, not a 403: whether a draft exists is not something the customer is told.

**Generating has a per-customer monthly allowance** (`app/reports/tbr/limits.py`, `FranchiseeConfig.self_service`, default 10, `manage_client.py report-config --generation-limit`). Generating is the expensive act in this product — every connector read for the customer, then a model call per section — and a page gives somebody no reason not to press the button again. It is per customer because a franchisee with forty customers is not the same spender as one with four; it counts **the franchisee's own generations and not ours**, so an engineer drafting on the same customer neither spends it nor is stopped by it and nobody is blocked by work they did not do; it counts **reviews that exist** rather than attempts, so a run that failed before anything was stored does not charge them for our outage; and the window is the **calendar month the generation happened in**, not the review's own period. Over it is a **429 with a sentence** naming the customer, both numbers and the date it starts again — not a 403, because they are allowed to do this and have done it enough times this month — and the page prints that message rather than folding it behind "Details", because for once the server's own words are the answer. Zero switches self-service generating off and says so differently, since "0 of 0" is arithmetic rather than an explanation. Generating over a period whose current review somebody else made is refused: superseding an engineer's work mid-review is not a self-service act.

Every generation, confirmation, dismissal, approval and release is an audit row with `actor_user_id` set (`report_generated`, `report_reviewed`, `report_rendered`), and `document.released_by` / `released_at` record who released it — kept on the document rather than read back out of the log, because it is shown beside the review and the record is not a lookup table. Inputiv staff see every review with who generated and who released each; an administrator is told only whether it is `mine`, because which of our engineers drafted a review is not something a customer's MSP is handed. `GET /audit` is Inputiv staff plus a franchisee's own administrator, with our people shown as "Inputiv staff" and the payload withheld.

**The page hides what a role may not do and that is a courtesy, not the control.** `app/api/reports.py` refuses by role on every route — `FRANCHISEE_REVIEW_ACTIONS`, `FRANCHISEE_APPROVABLE`, the mode check on `render` and `download`, and the allowance — and another organisation's customer is not reachable at all, because the client is resolved from the session and a site slug that is not theirs is the same refusal as one nobody has.

**An external identity provider is a later change, and the shape is here for it.** `Organisation.identity_provider` is the default for users created in it, `User.identity_provider` governs that user, and `User.external_subject` holds the provider's stable subject claim. Such a user has no password hash and no TOTP secret of ours. Only `local` is implemented, and nothing reads a password unless the governing provider is `local`, so adding a provider for one organisation does not touch another. Microsoft Entra itself is explicitly not built.

**Bootstrapping.** `scripts/manage_auth.py bootstrap` creates the Inputiv organisation and its first administrator, and is the only way an account is made without an invite. It needs database credentials, which is the point. `add-organisation` binds a franchisee's people to a client, and `suspend`, `activate` and `reset-password` all end the account's sessions.

**An invitation is a link, not a token.** `invite` prints the whole URL, built from `PUBLIC_BASE_URL` — which must be https outside `local`, because that link carries a one-time token, and settings refuse to start otherwise. The page at `/invite/<token>` is public, names who invited them and into which organisation, takes a password with a confirmation, and signs them in; `POST /auth/invites/accept` is what it posts to. One function, `describe_invite`, decides what a token is, so the page cannot offer a form for a link the endpoint would then refuse. Each of the five ways a link can fail — unknown, expired, already used, withdrawn, address already has an account — is a page with a sentence and a status that describes it (404, 410, 409), never a stack trace: a week-old link is an ordinary thing. A second invitation for an address is refused unless it replaces the first (`--reissue`, or `reissue: true`), because two live tokens for one address means whoever holds the older email uses it and the newer one then fails; `revoke-invite` withdraws one sent to the wrong place. Only a token's hash is stored, so a lost link is reissued rather than looked up.

## Agent loop

`app/agent/loop.py` receives `(user_id, client_id, message)`, loads the tool definitions from the registry, calls the model, executes tool calls through the factory (injecting `client_id`, and resolving a model-supplied site slug to a `site_id` within that client), feeds results back, and returns the final text. It enforces `MAX_TOOL_CALLS` and `TOOL_TIMEOUT_SECONDS` from settings, logs every step to `audit_log` (including the model's `stop_reason` on every call), and returns a structured error if a cap is hit. A `max_tokens` stop is returned as status `truncated` with whatever text was produced and a note that it was cut off — never as "no answer".

**Conversation threads.** A question is one turn of a thread (`app/agent/conversations.py`, tables `conversations` and `conversation_messages`). `run_agent` takes an optional `conversation_id`: absent, it starts a thread for the client and records `conversation_started`; present, it loads the thread and **raises if the thread's `client_id` is not the client the request is scoped to** — that is hard rule 1, not a soft check, and it happens before any model call and writes nothing — or if it belongs to another engineer or is archived. History is replayed ahead of the new question; the system prompt is not stored per turn, so the current version always applies. Rules that must hold:

- A user turn is stored as the engineer's question only; the client context (site list) is added once, to the first message, when the thread is assembled. Assistant and tool messages are stored as the verbatim Anthropic content blocks.
- A turn is repaired before it is stored (`finalise_turn`): an unanswered trailing `tool_use` is dropped, a paused turn and its resumption are merged, and a run that ended without assistant text closes with the answer the engineer was shown. A replay therefore never carries a `tool_use` without its `tool_result`.
- Stored messages are never edited or deleted. Over `CONVERSATION_CONTEXT_BUDGET` (80,000 estimated input tokens), the *replayed copy* is trimmed oldest-first — tool result bodies become `[result elided, N chars]` with the `tool_use` kept, then whole oldest turns go — never the newest `CONVERSATION_KEEP_RECENT_TURNS` (4), and a `context_trimmed` audit row says what was elided.
- Prompt-cache breakpoints sit on the system prompt and on the last historical message before the new turn.
- Threads are archived, never deleted. `audit_log.conversation_id` is `ON DELETE RESTRICT`: nothing done to a thread can remove or rewrite an audit row.
- Threads are per account; sharing is Phase 2. The owner is `owner_user_id` and the check is an identity check, not a courtesy. A thread started before sign-in existed carries only its engineer's handle and cannot be opened through the API at all: `check_access` refuses it rather than comparing a handle against a user id.

**Streaming.** `POST /chat/stream` is `POST /chat` as server-sent events, for an interface that renders progressively; the web page uses it. It is the same `run_agent` with an `on_event` listener: `started`, `model_call`, `text` (the model's text as it is written — the model call is streamed only when a listener is given), `tool_start`, `tool_end`, `web_search`, then `done` carrying exactly the `POST /chat` response, whose `text` is the answer of record (streamed text is a preview; text written before a tool call is not the answer). Rules: a listener changes nothing about a run — same tools, caps, result and audit rows, written when they always were — and a listener that fails or leaves never fails or cancels it (the run is its own task; it finishes, is audited and is saved to the thread). Events carry what the model asked for, never an id the engine injected. A refusal before any model call (unknown client, someone else's thread) is still a plain 400/403/404, not an event. `POST /chat` stays, unstreamed, for `chat_cli.py`, the selection check and Slack.

**Web search.** The loop also offers Anthropic's server-side `web_search` tool when `WEB_SEARCH_ENABLED` is true (default), capped at `WEB_SEARCH_MAX_USES` per request and optionally restricted by `WEB_SEARCH_ALLOWED_DOMAINS`. It is for the world outside the client — vendor error codes, KB articles, CVEs, product behaviour, end-of-life dates — never for a client's own data, and the tenant tools come first. Web content is untrusted: the loop never parses or acts on a search result (only a `tool_use` block the model emits runs a tool), the prompt tells the model to treat results as reference to summarise and cite, never as instructions, and to say when an answer came from the web and give the URL. Every search is its own `audit_log` row (`web_search`: the query and the URLs returned), per hard rule 4.

**Tool selection check.** `scripts/selection_check.py --client <slug>` runs the questions in `tests/selection/questions.yaml` through `run_agent(..., select_only=True)`: the real prompt, tool list and client context, stopped as soon as the model names its tools, so **no tool is executed and no vendor is called**. It reports the first tool called per question (`AgentResult.first_tools`), latency and tokens, and ends `N of M correct at T tools`. Run it after adding, removing or renaming a tool, or changing a description or the prompt's question map; add a question for every new tool and for each tool it overlaps. Below nine in ten, fix descriptions or remove tools before adding more. Harness runs are audited like any run (hard rule 4) and marked `interface = 'eval'` with actor `selection-check`, which no real entry point can send: usage, cost and feedback figures read `WHERE interface <> 'eval'`. Its threads are archived as soon as they are scored.

The system prompt in `prompts.py` is versioned. Changes to it are commits with a reason in the message.

## The pages

One product, fifteen pages: sign in, Ask, Reports, Sites, Coverage, Devices, Tickets, Integrations, Settings, the two Inputiv-only Autopilot pages — Results, which is the one nav entry, and the past-ticket labelling job, which is reachable only from it and is deliberately not in the nav — and the four Inputiv-only Automations pages: the runs for a client with the switches, one run, one workflow (read only), and a scheduled workflow's report. Server-rendered Jinja templates, one stylesheet, one plain JavaScript file per page. **There is no build step and there is not going to be one**; a new page is a template and a script, not a toolchain.

**The shell is rendered from the session** (`app/interfaces/web.py`). Who is signed in, what their role is called in words, which client they are on and that client's stored logo are all known before the HTML is written, so the header is right on the first paint rather than blank and then filled in. That is the *only* thing rendered from data: everything below the shell arrives from a JSON endpoint that resolves the session itself, so a template is never the thing deciding what somebody may see. The pages stay thin for that reason, not for tidiness.

**The header holds four controls and the nav holds one statement.** The client switcher (Inputiv staff only, as below); the command palette — everywhere this session may go, which is the pages this role is shown in the nav (`nav_pages`, handed over as `DESK.pages` so an entry inside a collapsed group is still reachable) and, for the staff who may switch, the clients the switcher already offers, loaded once on first open and never asked for by a session that may not switch; the theme toggle, whose label says which theme pressing it *gives* you because a control labelled with the state it is already in is a control nobody can read; and the account menu, which is where signing out lives. The nav can be narrowed to its glyphs (`data-nav` on the root, remembered as `desk-nav`), and then **the words go off screen rather than out of the document** — `display: none` takes a label out of the accessibility tree too, and nine links whose only content is an `aria-hidden` glyph are nine links called nothing — while the brand mark goes and the collapse button stays, because only one of the two is the way back. At the bottom of the nav, every page says what the application may do to a client's tools: read-only everywhere but the Automations pages, which say so in the other direction (`WRITES_HERE`), because a page that can write is the one where it matters.

**Nothing on a page is a number we do not hold.** A tile, a chip or a status that has no computed source does not exist — not a health score, not a delivery count, not a notification nobody raised. Whatever a mockup or a competitor shows, a figure arrives from an endpoint with its own definition beside it or it is left off.

Because the shell needs the session, the page routes are authenticated and a browser with no session is **redirected** to sign in (`redirect_unauthenticated` in `app/main.py`), carrying where it was going in `next`. Only a `GET` whose `Accept` names HTML: an API call keeps its 401, because a redirect reaches a `fetch` as a 200 full of markup. The sign-in page is the one public page and has no shell — no user to name, no nav worth offering.

**The frame does not scroll; what is in it does.** The shell is exactly the viewport (`height: 100dvh`, `overflow: hidden`), the left nav and the header are two of its grid rows, and `.shell-main` is the only thing with a scrollbar — so which product, whose customer and who is signed in stay on screen at row 200 of a 266-row table. The nav scrolls inside itself if it ever outgrows a short laptop; Ask keeps its own two scrollers and opts out with `.flush`. **Under 900px the nav is a drawer**: the same nav moved, behind a button in the brand block, closing on Esc, on its scrim, on following a link, and when the window is widened past the breakpoint. Opening it moves focus into it and closing it puts focus back on the button. **The shell and `.shell-main` are both positioned**, because `overflow: hidden` only clips a descendant whose containing block is inside the clipper: `.sr-only` is `position: absolute`, and with nothing positioned above it one hidden label per table row belongs to the initial containing block instead — which took the Devices page's document to 18,329px on a 900px screen and gave the window the scrollbar this rule says it must not have, with the frame looking right the whole time.

**Every box that scrolls says so twice.** The shell is the viewport and does not scroll; `.shell-main` does, and Ask manages two scrollers of its own. A flex or grid child that is meant to scroll needs **both** `overflow-y: auto` and `min-height: 0`, and a grid row that holds one needs `grid-template-rows: minmax(0, 1fr)` — the defaults (`min-height: auto`, an `auto` row) refuse to shrink below their content, so the box grows past the frame instead of overflowing and the `overflow-y` is dead code. Nothing errors when this is got wrong: the page loses its last paragraph and somebody finds out in a meeting, which is how the Ask feed ended up 5,945 pixels tall in a 724-pixel frame with the composer off the bottom of the screen and no scrollbar anywhere. `scripts/check_page_scrolling.py` fills every page past the screen and asserts its last element can be scrolled into view, and `tests/browser/test_page_scrolling.py` is the same check as a test; both need a browser, which this project does not depend on, so both skip without one. Ask follows its newest answer only while the reader is already at the bottom, so a stream never drags somebody away from what they went back to re-read.

**One height for every control in a filter bar.** `--control-height` is that height, and `.filter-bar` applies it to the inputs, selects and buttons in the strip above a list, so the labels above them line up and the row reads as one row. The stylesheet's input selector names the types that are **not** text boxes rather than the ones that are: the list it replaced did not have `search` on it, so the Devices search box was 21 pixels tall with a hairline border beside a 40-pixel drop-down and its label sat 19 pixels lower. A list of what to style has to be added to every time HTML gains a type; naming the handful that are not does not. Only `search` gets an `appearance` reset, and only because WebKit draws it as its own kind of box — a blanket one would take the calendar off a month input and the arrow off every select.

**Two pages may not show different numbers for the same words.** The Devices chips and the Coverage board answer the same questions — *what has no protection agent* — and used to disagree: measured on the pilot, the chip said 153 and the board said 126. The chip was asserting a protection gap on machines the RMM has lost, which the board deliberately does not, because a machine nobody has heard from may be in a cupboard and a gap on it is a finding about a machine that may not exist. The chips now use the board's population (`assessableByTools` in states.js: a computer NinjaOne is still reporting on), which took 153 to 124 against the board's 126. Two reasons for a difference remain and both are real: **when** — this list is as of the last daily resolution and the board as of its last snapshot, so a machine a tool dropped between the two is present here and absent there — and **what each holds** — this page knows every machine any tool ever returned, the board's population is NinjaOne's computers, so a machine only another tool holds is on the Not-in-RMM chip here and an unmanaged endpoint there. Every chip prints the population it counted and the page says where the rest of the difference comes from, because a reader who finds two numbers and no explanation has to assume one of them is wrong.

**A row's detail opens beside its list, not under it** (the Devices panel). A list is a place somebody is standing: its filters, its scroll position and its shape in the reader's head all survive if the detail is a panel over it and are all lost if the page grows a section below. The panel is a real modal dialog and behaves like one — `role="dialog"`, `aria-modal`, focus trapped in it, Esc and a scrim and a button to close it, and the keyboard handed back to the row it came from. **What is open is in the address bar** (`?device=<id>`, beside the filters), written with `pushState` so the browser's back button closes it, while narrowing the list is a `replaceState` because nobody wants to press Back through a filter. ↑ and ↓ step to the machine above or below in the *drawn* order, which is grouped by customer and so is not the order the API returned. A page that redraws its list on a history change would destroy the row it is about to focus, so it redraws only when the filters actually differ.

**A page per thing somebody works on.** The ticket queue is `/tickets`; one ticket is `/tickets/<number>`, its own page with its own address, back button and tab — the number Autotask prints, not an id of ours, because it exists before a workspace does and it is what somebody pastes into a chat message. The queue's filters ride in that page's query string, so the breadcrumb goes back to *that* queue and Previous and Next step through the same filtered list. The JSON routers are included before the web router, so `/tickets/list` and `/tickets/statistics` stay themselves rather than being read as ticket numbers; `tests/api/test_ticket_page.py` asserts it rather than trusting anyone to remember.

**Charts are inline SVG and there is no chart library** (`app/static/js/charts.js`), for the same reason there is no build step. Two rules, both from somebody reading a chart at a glance: **the number is always printed** — on the bar, or in a table under the chart — so length is never the only way to read a figure, and the two series that share one chart are told apart by a hatch as well as a colour. Each chart carries its numbers three more ways: a `<title>` per bar, an `aria-label` for a screen reader, and the definition the server sent with it.

**The nav is the roles.** An entry a role may not use is not shown: a viewer has no Ask, and `/` shows them Reports rather than a dead end. That is a courtesy and not the control — the endpoints behind each page are what enforce it — so a link appearing is never what makes something allowed.

**The client switcher is in the header, for Inputiv staff only.** A franchisee's client comes from their organisation and is printed as text; a picker would imply there were others. Switching is a server action that writes an audit row, so the page reloads from the new client rather than patching what is on screen: a stale panel from the previous client is exactly the mistake the switcher exists to make deliberate.

**The pages are calm.** A reader should be able to tell what a page is about from across a desk without reading a word of it, and that comes from whitespace and weight rather than from decoration. That decides the design system (`app/static/app.css`, which says so at the top), and the rules below are the whole of it — a change to a size or a colour is a change to this list:

- **Every colour is a token, and there are two themes.** Light and dark are two palettes of the same names (`:root`, `:root[data-theme="dark"]`, and the system default under `@media (prefers-color-scheme: dark)` guarded by `:root:not([data-theme="light"])`), and **a literal colour anywhere below the token block is a rule that is light-theme only** — nobody finds out until somebody switches. Which theme a person reads in is theirs, kept in this browser under `desk-theme` and applied by an inline script in the head (`_theme.html`, included by the shell *and* by the two shell-less pages) before the first byte of CSS paints, because common.js loads at the end of the body and by then the page has been drawn light. Both reads are wrapped: a browser with site data blocked throws on the first touch of `localStorage` and the page still has to render. The contrast of every ink against every ground is checked against WCAG AA — 4.5:1 for text, 3:1 for a dot, a hairline or the focus ring — before a value moves, and the focus ring is its own token so it can diverge from the accent.
- **Cards, not clutter.** A page is drawn on a tinted ground (`--ground`) and the things on it — a summary tile, a table, a grouped panel — sit on cards (`--panel`) held by a 1px hairline. **Cards do not nest**: inside a card, sections are held apart by space and a table there is borderless. Space still does most of the work: 40 to 48px between major sections, 20 to 24px between items in a list. No drop shadows in the dark theme, where a shadow on a dark ground is a smudge. A page is at most two columns: a main column and a ~300px rail about 68px from it. This replaces the old "no boxes anywhere, white ground" rule, which is why a control now carries a hairline too: on a tinted ground the old borderless fill and the page were a hundredth of a step apart, and the Settings page showed two invisible password boxes.
- **Three sizes, two weights.** 26px for a page title, 15px for body, 13px for metadata, labels and buttons; 400 and 600; line height 1.5, and 1.25 on a title. A section heading is not bigger text, it is heavier text with more room above it, which is why `h2`, `h3` and `h4` are all body size.
- **One primary action a page.** Filled accent, once. Everything else is a faint fill with a hairline, a link, or an item behind **More ▾**. Detail goes behind a tab, a slide-out panel or a link — never stacked under the thing it elaborates — and the explanation of how something works lives behind one link rather than on the page.
- **Consolidated metadata.** Facts about the thing are one subtitle line joined by `·`, not a column of label/value rows. A finding is one sentence with its source and date in a muted line beneath. Where a value can be changed, it is written inside a readable sentence with a dashed underline on the part that is editable (the ticket page's "Desk read it as"), and clicking it opens a small picker in place.
- **Status is a dot and a word**, 8px, never a filled badge and never colour alone: `--good`, `--warn`, `--bad` and `--neutral` are used for the dot, and the **word beside it** is what carries the meaning for a reader who cannot tell them apart. That is why `states.js` still gives every state a plain-language `label` — the glyph it also carries is now drawn as the dot (`.chip::before`) rather than printed.
- **Nothing is truncated, and nothing is ever shortened in storage.** No ellipsis, no `substring`, no shortened result summary. A table or a long value scrolls inside its own `.scroller`, which draws an edge shadow so a reader can see there is more. Half a device name on a wall is worse than a scrollbar: the reader cannot tell whether the rest was cut off or was never there. A table inside a scroller is `width: max-content` for the same reason — obeying `width: 100%` squeezed the columns until `SKG-WS-ACCOUNTING-04` printed as two lines, which looked considerate and was worse than either truncating or scrolling. **The one exception is the Ask rail's thread list** (`.thread .what`), where a question is clamped to two lines: a rail of three-line questions is a rail nobody can scan, and the thread is one of a list being chosen between rather than a value being read. It is allowed only because the shortening is in the drawing and nowhere else — the whole question is the button's `title`, it is in full at the top of the feed when the thread is opened, and it is stored whole. A title used to be cut to eighty characters by `title_from` before it was written to the database, which is the version of this that is never allowed: no page could get the rest of the question back.

**One vocabulary, in one file.** Every internal state a page prints — a device's status, the coverage board's per-tool verdict, how a vendor record was paired, an SLA clock, how sure we are which machine a ticket is about, what an engineer did with a plan step, what kind of machine NinjaOne says it is — is named once in `app/static/js/states.js`, loaded before every page script. Each state carries a plain-language `label`, a one-line `reason`, a chip `tone` and a `mark`. **Colour is never the only signal**, and what enforces it is the `label`: a chip is a dot and a word, and `stateChip` cannot draw one without the word. (The `mark` glyph is kept on every state and is no longer printed — the dot took its place — so a state is still never defined by its colour alone in the file either.) Coverage, Devices and Tickets all read from it, so the board and a device page cannot call one thing two things, and the Coverage page's "what the states mean" list is generated from the same entries as its chips. Vendor field names that are not our states (GravityZone's sixteen module keys, seven of them undocumented) are turned into words by a transform, `fromCamel`, rather than a mapping, so a key nobody has seen still reads. **A page may derive a verdict the data does not store** — the one overall mark per device is `deviceHealth`, computed from the resolution's status and which tools hold a record — but then the page prints the rule it used, and the derivation mirrors the board's population rule (`AGENT_NODE_CLASSES`): a switch with no protection agent is not a gap.

**A link out to a vendor's console is built from ids we hold and an address we were given, never a guess** (`app/interfaces/consoles.py`). A NinjaOne tenant is on one of several instances and an Autotask tenant on one of nineteen numbered zones, so the console host is derived from that client's own stored `ToolCredential.config` — the non-secret half, never `get_secrets()` — and a host we do not recognise yields no link, with the vendor id shown to copy instead. GravityZone and ConnectSecure have no address for one record that we can build, and are deliberately absent rather than approximated. The routes are recorded in `docs/api-notes/<vendor>.md` and are not yet checked against a live console.

**Untrusted text is escaped, including in attributes.** `escapeHtml` in `common.js` escapes quotes as well as angle brackets: the obvious `textContent` round-trip does not, which is safe between tags and a hole inside `value="…"`. Model output is rendered through `marked` and then sanitised with `DOMPurify` before it is inserted, and nothing else on a page reaches `innerHTML` unescaped.

**Static assets are stamped with the file's own mtime** (`asset()` in `web.py`), not the application version. A version string is the same all through a development session, so an edited stylesheet was served from cache and the change appeared not to have happened. An mtime changes exactly when the file does, which is also what a deploy wants.

**Two routes may not claim the same method and path.** `duplicate_routes` refuses it at build, beside the scope declaration check: whichever router was included first answers and the other disappears without an error anywhere, which is how the Sites page and its own JSON endpoint both ended up called `/sites`. The data route is `/sites/list`, nested under the feature as `/reports/tbr` already is.

## Integrations

`app/api/integrations.py` and `/integrations` answer one question per
connector: is this franchisee set up on it, how many of their customers are
mapped, and when did a read of it last succeed or fail.

- **Nothing on it calls a vendor.** Every value is a row somebody wrote at the
  time. A "check it now" button would be six vendor calls on a page load and
  would answer about that moment rather than about the work the product does.
- **Set up is the factory's answer, not a credential row** (`why_not_configured`),
  the same function the ticket panel uses to tell "not set up for this
  customer" from "the read failed". A demo client holds no credential and its
  connectors work; a live client with a row we cannot build a connector from is
  not set up either.
- **The window is `WINDOW_DAYS` (30).** A success in August is not evidence
  that something works today, so a read older than that is not an answer and
  the tool reads "No reads" — which is what it is, rather than a verdict on the
  vendor. `interface <> 'eval'` as everywhere else, so the selection check's
  own runs are not somebody's work.
- Four states and no fifth: `Not set up`, `Answering` (the last read
  succeeded), `Failing` (every read in the window failed), `No reads`. Two of
  the four are grey on purpose: not being set up and nobody having asked are
  not faults. The header's row of vendor marks stays what it is — **set up,
  never healthy** — and this is the page its docstring points at.
- **A card a tool, and the rest behind a drawer.** A table row is the wrong
  shape for a paragraph: what there is to say about one integration is what
  Desk uses it for, what it reads, how read-only is kept and when it last
  answered. The card holds that in the order somebody reads it and the panel
  (the one the Devices page opens a row into) holds the detail — every
  customer mapped, the last few reads, the read-only scope, and what connects
  it. The drawer counts customers the way the card does, mappings with the
  inactive ones said to be inactive, because one number on a card and a
  different one under it is a page contradicting itself.
- **The chips are reads the connector makes, and nothing else.** `READS` is
  the list; a chip for a capability the vendor has and we do not use is a
  claim the product does not keep.
- **A failure is a sentence, and the class name is for the log.**
  `UpstreamError` on a franchisee's screen is a stack trace with the stack
  taken off. `ERROR_WORDS` maps each kind to plain words with the vendor
  named, and a kind nobody has mapped reads "The read of Cove did not work."
  rather than falling back to the raw name — a fallback to the name is no
  fallback. The name itself is sent to Inputiv staff only and printed only in
  the drawer, beside the sentence; so is the command that connects a tool,
  because a franchisee cannot run it. The map is the kinds that actually
  happen, counted over the record, not every class that exists.
- Every role reads it: a franchisee administrator asking why a number is
  missing is asking this page's question.

## Business reviews (TBR)

`app/reports/tbr/` generates the Client Business Review against `docs/reference/tbr-template.pptx`, slide by slide as `docs/reference/tbr-slide-map.md` lays out. It reads through the same connector factory as the tools (hard rules 1 and 5), is read-only, and audits every connector read, model call, review action and render (hard rule 4). Run it with `scripts/tbr.py` or the `/tbr` screen; settings are per franchisee (`manage_client.py report-config`). The rules that must hold:

- **Numbers come from code.** Every count, percentage, date, price and hour is a `Fact` with a stable id, a definition and a display string formatted in code (`collect.py`). A fact says whether it covers the review period or is the state at generation: NinjaOne keeps no history, so device and patch-backlog facts are always as-of. A source that fails is a recorded `Gap`, never a zero.
- **Findings are decided by rules, only phrased by the model** (`findings.py`). A `measurement` is asserted from one tool. A `gap` — a claim that something is *absent* — needs two tools, or it is held for an engineer to confirm and stays off the deck. Comparisons use the previous period's stored facts only; with no snapshot, no improvement sentence is written.
- **One model call per section, slot by slot** (`narrative.py`). The model sees only that section's facts and findings, fills named slots, and may not type a digit: a value is a `{{fact.id}}` token that code substitutes, and a token is a citation. A draft that breaks a rule is retried once, then the section uses the findings' code-written wording and says so. Every rendered sentence carries the ids it rests on; that trace lives on the stored review and in the review screen, whatever is rendered.
- **A slide holds what its placeholder measures, and one config says how much** (`layout.py`). `SLIDE_BUDGETS` declares, for every model-written slide (5, 6, 7, 11, 14, 18, 3), its item cap, characters per item and per slide, and a size ladder from the template's size down to a readable floor; the numbers are set by rendering each slide at its budget and measuring, and `tests/reports/test_tbr_layout.py` renders each at its maximum (with the longest lead code can put on it) and asserts nothing exceeds the placeholder, and at one item asserts it takes the template's size. The brief tells the model its `max_chars` per slot and `slide_max_chars` up front; the validator refuses a draft over either; and the renderer measures anyway (`layout.fit`): the largest size that fits, then whole items dropped from the least serious end with a code-written line saying so, then sentences. A code-written line with no slot (the suspected-findings caveat) is measured and never dropped. Sizing by counting paragraphs is what put a fifth service under the footer; no model-written slide is sized that way. A finding backs a catalogue service only when that service addresses it directly (`service_key` in `findings.py`); where none does, it backs nothing and stays off slide 18 rather than pointing at the nearest name. Hardware Lifecycle Planning is for age or end of support, which until device age is collected means only Windows 10 devices that cannot run Windows 11; a full disk, short memory or an in-place Windows 11 upgrade is a priced job on slide 13, not a service.
- **Three render modes** (`render.RenderMode`). `client`, the default, is what the customer receives: speaker notes are empty or hold only the talk track an engineer wrote for that slide (`review.set_talk_track`), never fact ids. `internal` puts the fact-id trace in the notes. `demo` replaces every client, site, device, contact, logged-in user, NinjaOne location and engineer name with a consistent pseudonym (`demo.py`: one mapping per document, so the same real name is the same pseudonym on every slide, chart and note; a location is replaced whole and before the site name inside it, so "Acme Legal - Houston" is `Location A`, not the site's pseudonym with an office left standing), keeps every number, stamps "Sample data" on every slide, and names the file without the customer. **The demo gate is stricter than the replacement**: `real_name_terms` lists every site and client name and slug, contact, device, logged-in user and location the review holds (three characters or longer), and the deck's and the PDF's gates refuse the file if any appears as a substring, case-insensitive, in anything drawn (`substring_survivors`), so a name inside a vendor free-text field the mapping never saw is caught; the replacement itself stays whole-token so a device called `RECEPTION` never rewrites the word, which also means such a device makes the word a gate hit in a demo. The template ships its own speaker notes (slides 1, 3, 6, 7: presenter instructions and AI prompts); every mode clears them. Only a client render marks a review `rendered`, and any change to a review makes every deck stale.
- **People's names are a franchisee setting with a per-review override.** `FranchiseeConfig.show_people_names` (`manage_client.py report-config --show-people-names | --hide-people-names`; off by default, on for the pilot) decides whether client and internal renders of the deck and the PDF name people: the tickets-by-contact chart, the lifecycle tables' last logged-in user and a location named after a person. Off, they print as `Contact A`, `User A` and a withheld location. An engineer overrides it for one review (`review.set_contact_names`: True, False, or None to follow the default again; who set it is recorded, and a stored review from before the setting existed reads as no override), `ReviewDocument.people_names_shown` is what a render reads, and the gate refuses a named chart only while the effective setting is off. Changing the franchisee setting (`config.set_people_names`) copies it onto every current review's snapshot and marks each changed, so every deck and PDF is stale and a released review is unreleased until rendered again, and writes a `report_config_changed` audit row naming the reviews (migration 0019). The stored chart keeps the names either way. A demo render pseudonymises everyone whatever the setting says.
- **Workstation or server is decided by the operating system where it can be, once, for both outputs** (`hardware.device_role`). Windows is a server only when the OS name contains `Windows Server`, otherwise a workstation whatever NinjaOne's node class says (live: a Windows 10 IoT till classed `WINDOWS_SERVER`); macOS is a workstation; Linux, an unknown OS and everything else take the node class. The collector decides it per device in the inventory step (`Collector.ninja_roles`, the basis kept on each), and the deck's workstation, physical-server and virtual-server counts, the low-memory workstation list and the PDF's lifecycle tables all read that one decision; the agreement test asserts the lifecycle rows are the counts. Devices whose OS and node class disagree go in an internal-only table (`ninjaone.devices.role_disagreements`) that the internal PDF prints under the lifecycle tables and the internal deck lists in the notes of the slide with the counts. A site with no servers gets a server table with no rows, and the PDF prints "No servers at this site" from it rather than a blank grid.
- **Value delivered** is a code-written block on the Accomplishments slide: patches installed, alerts resolved, tickets resolved, tickets resolved outside business hours. Each is a fact with a definition; a figure the connectors cannot supply, or a zero, has no line. Alerts resolved comes from NinjaOne's activity log and only when the log still covers the whole period (it is kept for about two weeks and truncates silently: docs/api-notes/ninjaone.md). Out-of-hours needs the franchisee's `business_hours.timezone`; there is no default and one is never guessed.
- **Slide 14 needs two tools per gap** (`security.py`, `findings.py`). NinjaOne computers are joined to Bitdefender endpoints by hostname within the site; a NinjaOne computer with no Bitdefender endpoint is the "no protection agent" gap. A module that is off produces one of two findings, never conflated in wording: `disabled` is a Cybersecurity finding, `not_licensed` a Recommended Services one, both under the same cross-tool rules; `not_reported` produces nothing. The Bitdefender patch module is a gap only where NinjaOne is not patching the device, and "NinjaOne patching it" means an install in the last 90 days or any row on its waiting list (`collect_patch_coverage`), not only the review month's installs; encryption is a gap only when neither BitLocker (NinjaOne volumes with `include=bl`) nor the Bitdefender encryption module protects it; the EDR sensor, disabled or unlicensed, is always held for the engineer until Blackpoint can corroborate it; Exchange and container modules are never findings. NinjaOne's held antivirus finding is confirmed by Bitdefender showing a doubted device without a working agent, or by the hostname join finding no Bitdefender endpoint for it at all (that count is its own fact, `antivirus.unprotected.no_endpoint`, so the sentence never cites the site-wide NinjaOne-only figure for it); dismissed (with an internal note) when every doubted device is protected; and left held when Bitdefender does not know the device. Security on the scorecard is scored from these; a site with no GravityZone company shows "No data".
- **Slide 14's vulnerability findings come from ConnectSecure joined to NinjaOne** (`vulnerabilities.py`). Ranked: known-exploited (CISA KEV) findings first as a critical measurement; then "a few updates resolve most critical findings" (the top three fixes' share of critical findings, `connectsecure.remediations.top_critical_percent`); then open critical findings; then software to remove (`Uninstall` remediations, their own finding type; `Run remediation script` is an engineer action and never a client recommendation); then scan coverage (NinjaOne computers with no ConnectSecure asset or not scanned in `CONNECTSECURE_STALE_SCAN_DAYS`, a two-tool gap). **A fix is a target version, not a KB number** (live: 0 of 300 fix texts carried one), so "fix awaiting install" needs a normalised product match against a NinjaOne pending software patch whose version is at or above the target; anything else stays an open finding, and an OS update stays unmatched unless a KB does appear. The match rate is an internal-only fact, never rendered in client mode. A slide takes at most its budget's `max_items` findings (`layout.SLIDE_BUDGETS`) and says how many were left out. Vulnerabilities are state, not events: the facts are as-of the scan dates, they sit on the stored review that is the next review's snapshot, and they are `COMPARABLE`; nothing goes to the daily collector. The Security scorecard's vulnerability metrics (known-exploited count, share of assets with a critical finding, share of managed computers unscanned, the company risk score) are in `scorecard.toml`; a site with no ConnectSecure company records a gap and those metrics are left out.
- **A fact declares the scope it counted, and a sentence may not mix two scopes.** Scope is `Fact.population` (`universal`, `confirmed` or `unconfirmed`: ConnectSecure's two populations, everything else universal) together with `Fact.severity` (`all`, `critical`, `high`, `medium`, `low`, or `None` when the fact is not a count of findings). `Fact.denominator` names the fact a share is a share of, and `Fact.internal_only` marks a fact an engineer may see and a customer never does (the awaiting-install match rate, the day's request count). The narrative validator rejects a drafted sentence citing facts of two populations — that is how "240 critical findings across 4 devices" reached a deck, a suspected count beside a confirmed device count — or of two severities, which is how a caveat counting every severity came to sit under a headline counting criticals. The one exception is a fact cited as another's denominator: "M of the X open critical findings" is one statement, so the total may be a wider scope than the part. Any sentence citing an internal-only fact is rejected outright. The suspected findings get exactly one code-written caveat sentence on slide 14, counting the same severity as the headline it qualifies, and are cited by nothing else.
- **A percentage prints the number it is a share of, or it is not printed.** A fact whose display ends in `%` must name a `denominator` fact, and the sentence must cite that fact too; the validator rejects both a share with no denominator and a share whose denominator is missing from the sentence. A percentage whose denominator is a filtered subset nobody publishes is `internal_only` and the customer's sentence states counts instead: "3 updates resolve 100% of the critical findings the recommended fixes address" was a share of a number that appeared nowhere, and beside a headline of 118 open criticals it read as all of them.
- **The scorecard is rules, in one file.** `app/reports/tbr/scorecard.toml` holds every area, metric and threshold and documents how they are applied; `scorecard.py` only applies them. Service, Devices and Patching are good, attention or action (an area takes its worst metric; with no facts it is "no data"). Security and Backup print "Not yet assessed" until their connectors exist. A trend arrow appears only when a prior snapshot exists, and up always means better. The model never sees or writes a status. Chip colours are never `FF0000`, the template's placeholder red.
- **No Users line on slide 5.** Autotask contacts are not users: the count is not collected, and a stored review that still carries one renders without it. The Microsoft 365 connector could now supply it — a tenant's enabled member accounts are a real count — and putting it on the deck is its own task, with its fact definition, its slide budget and its gap when a customer has no tenant mapped. Until then the line stays off rather than being filled from the nearest number.
- **Industry Trends is the only web section.** The model is given the industry string and nothing else; every query is audited and one naming the client voids the research; a trend's URL must be one the searches returned; and it is never rendered without an engineer's approval. Any later change withdraws the approval. Report research has its own allowlist, `REPORT_WEB_SEARCH_ALLOWED_DOMAINS` (regulators, standards bodies, industry associations), separate from the chat agent's; settings refuse a vendor domain or an empty list, and a trend whose source is off the list is dropped in code as well as by the API.
- **Prices and hours come only from the franchisee's price book**, otherwise the slide prints "Quote pending". Nothing estimates one and the model never sees one.
- **No data, no slide.** A section is `filled`, `awaiting_engineer`, `dropped` or `deferred` (a later connector). Only a filled, approved section renders; a divider goes with its section; the agenda loses the line. Slide 20 and the dividers are static.
- **The render gate is last and trusts nothing** (`gate.py`). It resolves text colour at the run, the paragraph default and the shape's list style, and refuses to write a file if any red text, any string on the map's list, any template sample text, the slide 6 screenshot or a sample CX score remains. Speaker notes are checked too, against the template's own notes and nothing broader (`note_problems`): in any mode a note fails if it holds a line of the template's notes (read from the template file, any run of five consecutive words) or a fill-in mark from the map (`XX`, `ABC Company`, `202x`, `{`, `<<`). The map's ordinary phrases ("talk track", "Insert", "List recent") are refused on slides only, so an engineer's notes may use them. Beyond that: anything but the talk track in a client or demo deck, and any surviving real name (slide text, chart labels, notes) in a demo deck. Add to `TEMPLATE_SAMPLES` when the template gains sample content that is not red.
- **The Monthly Report PDF is the review's second output** (`pdf.py`, `monthly.py`), rendered from the same stored facts, tables and charts as the deck with no model-written text anywhere on it: Ticketing (the daily created-and-completed chart with the deck's totals, the first-response and resolution gauges with the franchisee's target and the facts' definitions, tickets by contact under the deck's contact-privacy setting with automated contacts as a separate count, tickets by issue type and, when unset or Other is over half, by sub-issue type or a note saying the field is largely unset), Monitoring (OS and third-party patch installs for the period with the failed devices; workstation and server lifecycle tables with storage banded 40%+ healthy, 20 to 39% low, under 20% critical, `not reported` where NinjaOne said nothing, never a zero, and an estimated age from the processor family's launch year, blank when unknown and footnoted with the method) and Backup (`not yet assessed` until Cove exists, the cards and table it will fill drawn empty, and coverage against NinjaOne workstations recorded as a gap). ReportLab draws it (pure Python, vector charts, no system package, so it runs on Render's native runtime). The approval step is the review's `monthly_report` section, slide 0, code-written items, never on the deck: a client PDF refuses until an engineer approves it, an internal or demo PDF renders before that stamped as a draft, and any edit withdraws the approval and empties `renders` for the deck and the PDF together (keys `pdf/<mode>`). The gate runs on every string drawn: no token, no placeholder, no contact or logged-in user name while names are private (`User A`, `User B`; a location named after a person is withheld too), no real name in a demo. Every fact the PDF draws is recorded by id and `tests/reports/test_tbr_monthly_pdf.py` renders both outputs from one review and asserts every shared number and every shared chart value is identical. Same routes: `POST /render` with `output: pdf`, `GET /download?output=pdf`, `tbr.py render --pdf`, the Render PDF button on `/tbr`; a franchisee downloads the client PDF only once the review is released by its client deck.
- **The Backup section is Cove, and every figure in it says what it counted**
  (`app/reports/tbr/backup.py`). The headline is two numbers because Cove counts
  a customer's Microsoft 365 tenant as a device: "5 protected: 4 devices + 1
  Microsoft 365", and every count about machines excludes the tenant. The
  retention distribution is Cove's **product** (`I10`: `All-In`, `Documents`,
  `90D-52W-36M-7Y`), not its retention units, which is the coarser scheme
  behind it. **The success rate is the 28 days Cove keeps, ending when the
  review ran** — the state at generation, never the review period, printed as
  the two dates it covers and `period_bound=False`; the trend is labelled by
  review date, because two reviews generated on the 3rd and the 27th cover
  different windows and month names would invite a comparison neither supports.
  A day counts as a success when the backup completed, including with errors
  (counted and listed apart, because the data is kept and somebody still has to
  look); failed, interrupted, aborted and a day with no session at all count
  against. **The status word beside a device is where it stands now and is not
  a window at all** (`status_of`): what the last session did, and how long since
  one succeeded. A machine that failed a fortnight ago and has backed up every
  night since is backed up — the month's failures are history, and history is a
  column of its own on the device table ("Failed or missed days") rather than a
  word that says the wrong thing about today. The four words are in one place
  for both outputs (`STATUS_WORDS` for the document, the `backup` family in
  `states.js` for a page); a key like `not_backed_up` never reaches a reader. **A device nothing ever ran on is 0%, never "no failures"**, a device
  younger than the window is measured over its own life, a session still
  running today counts for neither half, and a day whose character could not be
  read is out of the denominator and said so on the page. A rate is a share of
  days and never an average of per-device percentages. The coverage gap — a
  NinjaOne machine with no Cove device — comes from the coverage board's join
  and not a second one (`COVERAGE_TOOLS`, the Backup entry's reader), matched
  on the name with Cove's own `_xxxxx` suffix removed, which is a rule and not
  a certainty: it is phrased "not backed up by Cove" and never as a machine
  having no backup. **Which machines count as a gap is the site's backup scope**
  (`effective_scope`), read by the review, the ticket panel, the coverage board
  and the Ask tool alike. An explicit per-site setting always wins; `auto`
  **asks how many of the site's workstations are backed up, not whether any
  is** — at least `BACKUP_AUTO_WORKSTATION_SHARE` (0.5, as `sync_overlap_share`
  is, and the same kind of judgement about whether a handful of rows is a
  pattern) or the ones Cove holds are exceptions rather than a policy. The
  older rule said "any", and on the pilot one backed-up laptop at a 107-machine
  customer turned the other 106 into gaps reported every month; measured, the
  board's Backup coverage went 5.4% → 11.7% (scope applied) → 48.5% (this
  rule), with 538 machines out of scope across 24 sites and the remainder
  genuine findings about servers. A site mid-rollout is the case `auto` gets
  wrong and is set explicitly. **Where `auto` lands on servers only and somebody is still
  backing up a workstation there, the decision carries `mixed`**: the rule has guessed, and
  the guess is what took the remaining workstations off the gap list. The board marks the
  site ("Confirm backup scope"), the Ask tools say it in the answer, and the review records
  it as an `internal_only` fact — never a client deck or a client PDF, because "our rule is
  unsure about your estate" is a sentence about our rule. One explicit setting settles it. A site with no Cove customer gets one line saying so.
- Reports are scoped like everything else: a report id is only ever looked up together with its client, and another client's id is a 404. Reviews are superseded, never deleted; the previous period's row is the next one's baseline. `tbr.py generate-all` drafts every active site of one client that has a NinjaOne or Autotask mapping, one after another, past failures; it skips a site that already has a review for the period unless `--regenerate` is given, so a batch never replaces an engineer's work by accident. Rendered decks hold customer data and are written under `REPORTS_DIR`, outside git.

## The demo tenant

`app/demo/` is a fictional franchisee (Tailwind IT Services, eight customers named like Contoso and Fabrikam) generated from a seed and served by fake vendors: `dataset.py` builds the world (about 250 computers plus a switch each, ninety days of tickets, patch installs, alerts, detections and vulnerability findings, every timestamp an offset resolved at serve time), `vocabulary.py` holds the public words it is built from (Windows KB numbers, CISA known-exploited CVE ids, common software titles, hardware models), `scenarios.py` lists what the world must contain and `check(world)` proves it, and the six `*_api.py` modules answer each vendor's HTTP API from the world behind `httpx.MockTransport`, so the **real** connector clients run against them unchanged, guards, pagination and error mapping included (docs/demo-tenant.md). The rules:

- **Live and demo never cross.** `Client.kind` is `live` or `demo` (migration 0020). The factory builds a demo client's connectors only from `demo/connectors.py`, whose classes are the real clients over the fake transport and cannot be constructed without a `World`, so the live path can never produce one; a live client is built only from the real classes and, with no credential, is refused rather than given a fake. A demo client holds no credential and `set-credentials` refuses it before asking for a secret. The fake transport raises on any host that is not the fake vendor's.
- **Every audit row for a demo client is marked** (`audit_log.demo`, set in `record_event` from the client's kind, kept per process), so demo traffic is told apart in every figure read from the table, and `demo_tenant.py delete` may remove those rows and no others.
- **Nothing in the world came from a tenant**, and a scenario is placed by name, never left to chance: the coverage states (a NetBIOS collision, unmatched twins, `rmm_stale`, `rmm_agent_down`, unmanaged, default Windows names, external targets, discovered rows, network gear), a customer with two GravityZone companies, an AV-only customer, encryption unlicensed with BitLocker on most devices, EDR licensed on one customer only, a Windows 10 IoT device classed as a server, confirmed and suspected criticals with known-exploited ones, version and uninstall remediations, SLA breaches, automated contacts, repeat issues, and patch failures. `tests/demo/test_world.py` fails if one is lost. `excluded` is left to the person giving the demo.
- **The world has six vendors, Cove among them.** `DEMO_CLIENTS` maps NinjaOne, Autotask, Bitdefender, ConnectSecure, Cove and Microsoft 365. Backup is the one of the six that is sold per machine rather than rolled out to a fleet, so the world is built that way: **two of the eight customers buy no backup at all** and have no Cove partner, which is what gives the board a whole customer to say `not assessed` about instead of counting every one of their machines as a gap; where it is sold it is on every machine, which is the gap the Backup column is actually for. Cove holds each buying customer's Microsoft 365 tenant as a device row of its own, told apart only by `I59`, so the demo exercises the rule that every count about machines excludes it. The named cases are a server eleven days behind, a device nothing has run on for two months that may or may not be retired, a session that completed and could not read a handful of files, and two servers at a buying customer that Cove holds no device for (`scenarios.py`, the `backup.*` entries).
- **`scripts/demo_tenant.py create | reset | delete`** manages it: `create` registers the client, runs the same site sync a live client gets through the fakes, writes its report settings, creates the demo franchisee organisation and prints invite links for a demo admin and a demo viewer; `reset` deletes what the tenant accumulated and syncs again; `delete` removes everything including the organisation and its accounts. Microsoft 365 is the one connector `create` maps by hand, because it cannot be synced.

## Microsoft 365

`app/connectors/microsoft365/` reads one end customer's Entra tenant: who is in it, what they are licensed for, who has a second factor, what the groups are. `docs/m365-connector.md` is the operational page (the two access routes, the consent link, every permission and what it is for, what to ask a customer's administrator) and `docs/api-notes/microsoft365.md` the vendor findings. The rules:

- **Read only, and enforced here rather than trusted to the vendor.** The client refuses any method but `GET` before a request is built (`ReadOnlyViolation`, no HTTP made). Graph has read-only `POST` query endpoints (`/$batch`, `getByIds`, `getMemberGroups`) and `READ_ONLY_POSTS` is the allowlist for them: it is **empty**, because none is needed. No write permission is requested and no write method exists.
- **A tenant is a site, not a client.** Every other connector gives us one tenant holding every customer; here each end customer has their own, consented separately. So the credential is the client's (our multi-tenant application, certificate preferred over secret) and the **tenant id is the site's `ToolMapping.external_id`**, with one token per tenant and one tenant read at a time (`for_tenant`, `read_each_tenant`). A client with more than one tenant mapped must name the site: answering for all of them would merge two companies' directories into one answer.
- **It cannot be synced, so it is mapped by hand.** A Graph token is for one directory and cannot enumerate the others, so `list_organisations()` refuses and `manage_client.py map-site` puts a customer's tenant id on their site, refusing an id another client holds exactly as the sync does.
- **A premium-licence item or a permission nobody consented to is a sentence, never an error and never a zero.** `signInActivity` needs Entra ID P1 or P2; Microsoft's registration report leaves out disabled accounts, so a disabled account's second factor is unknown rather than absent; a tenant that conceals names in its usage reports gives mailbox rows that cannot be joined to anybody; `MailboxSettings.Read` is what tells a shared mailbox from a person, and without it the MFA gap reads larger than it is. Each is carried as an `Unavailable` item with the reason, printed by the profile under "Not available for this tenant" and on a ticket under the reading it belongs to.
- **Counts and ids are what is stored; names are what a page prints.** `Profile.as_dict` — what the audit row carries — is counts and ids only. The profile prints the addresses with no MFA because that is the answer somebody asked for; `m365.py people` prints ids, as `devices.py` does.
- **Shared mailboxes and rooms are not people.** They are enabled member accounts in Entra that cannot register a second factor, so MFA coverage reads their mailbox kind (bounded by `MAILBOX_KIND_READS`, and only for the accounts that look like they have none) and counts them apart. On the demo that is 9 of 14 rather than 9 of 17.
- **The join to the rest of the estate is light and stores nothing** (`app/devices/people.py`): an account to an Autotask contact by email, and to the machines it is the last logged-on user of through the identity layer, on the ticket page's own login rules. No people table, no link row, no queue. **Microsoft 365 is deliberately not on the coverage board**: that board is about agents on machines.

## Coverage

`app/coverage/` answers one question fleet-wide: for every NinjaOne managed computer and every tool that should have an agent on it, does the tool know the machine, and is what it knows current? The rules:

- **One join, three readers.** `core.assess` is the join and the only one: the board (`compute_coverage`), the chat tools (`count_coverage`, `list_coverage_gaps`) and the review's "no protection agent" and scan-coverage derivations all call it, on the same per-row verdicts (`config.bitdefender_endpoints`, `config.connectsecure_endpoints`), so the deck and the board cannot disagree; `tests/coverage/test_agreement.py` feeds both the same recorded inventories and asserts the same names. A GravityZone row with no agent on it is `absent`, the same gap as no row.
- **The population is NinjaOne's computers** (`is_agent_class`: workstations, servers, VM guests); network gear, phones and hypervisor hosts are counted and left out. **A device's hostname is the host part of its full `dnsName`, else `systemName`** (`NinjaDevice.hostname`): `systemName` is the 15-character NetBIOS name, and machines whose names differ only after the fifteenth character collide on it (live: 77 of 1,024 pilot computers carry a longer `dnsName`; five machines at one site shared two NetBIOS names). Matching is by normalised hostname **within one site and never across two**; a device with no hostname is `unmatched`, and two at a site sharing one are told apart by a MAC or a serial or left `unmatched` naming each other, never guessed.
- **Four passes, each one-to-one within the site, each recorded.** Exact normalised hostname; then the NetBIOS 15-character key (for the tool that holds the truncated name where NinjaOne has the full one, or the reverse); then a shared MAC (Bitdefender `macs` and ConnectSecure `mac` against NinjaOne's `network-interfaces` query); then a shared serial (ConnectSecure `serial_number` against NinjaOne's `computer-systems` query, placeholders dropped by `config.serial_key`). **When a name pass is ambiguous** — two devices share the key, or the key names several machines in the tool — **a MAC then a serial decide among the candidates** before anything is declared unmatched, counting only values no rival device carries (a MAC three laptops report is a docking station, not an identity). `ToolState.matched_by` says which pass paired a device; what nothing tells apart stays `unmatched` with the candidates listed and `found_by` naming the pass, never paired with the nearest. **A machine in a tool is the rows sharing one exact key at one site unless their MACs or serials say otherwise** (`core.group_machines`): a reinstalled agent's two rows are one machine, three rows a scanner knows by one truncated name are three; the split only matters when several devices need telling apart, and a lone device whose key names several machines takes them all as it always did. Nothing is matched across sites.
- **Nine states, one config.** `covered`, `stale`, `absent`, `unmatched`, `rmm_stale`, `rmm_agent_down`, `excluded`, `not_assessed`, `not_in_scope`; the thresholds behind `stale` are `config.STALE_RULES`, each with a definition the page prints. A device NinjaOne itself has not heard from in more than `COVERAGE_RMM_STALE_DAYS` (default 14) **takes part in the join like any other**: paired with a row the tool has heard from within the same window it is `rmm_agent_down` — machine alive per Bitdefender or ConnectSecure, NinjaOne not reporting — a finding on its own line, and its row is never listed as unmanaged as well; paired with a dead row, or with nothing, it is `rmm_stale`. Neither counts as absent from another tool. **A date is the only evidence of life** (`core.endpoint_alive`): ConnectSecure's last scan; GravityZone's last successful scan, which the listing returns in bulk with `includeScanLogs` and which is the first evidence; or the `lastSeen` of `getManagedEndpointDetails`, one call per row, which no list method returns (api-notes). That call is made only for the rows paired with a device NinjaOne has lost for less than `DEVICE_RETIRE_DAYS` and not alive by scan date — a device lost for longer is not checked and its verdict says so (`core.mark_unchecked`) — under `BITDEFENDER_DETAIL_CONCURRENCY`, and the answer is kept on the record's `DeviceVendorLink` (`vendor_last_seen_at`, `vendor_checked_at`, migration 0018) and read back from there for `BITDEFENDER_LAST_SEEN_REFRESH_HOURS` (12), so the board, the resolution and the review share one read a day (`app/devices/lastseen.py`: `candidates_for`, `read_last_seen`; the join runs once to find the rows and once more with the dates; every run logs lost devices, alive by scan date, beyond the window, from links, fetched, and the snapshot keeps the counts in `reads`). An agent installed is no evidence: live, 91 lost devices kept a GravityZone row and 43 of them had been unseen by NinjaOne for over ninety days. `config.COVERAGE_TOOLS` is where a tool is added: Backup is listed with no reader and is `not_assessed` until Cove exists, and wiring Cove in is one reader on that entry with no caller changed. **Microsoft 365 is not on this board and is not going on it by default**: the board is about agents on machines, and an account is not an agent. A tool with no credentials, or no company for a site, is `not_assessed` there, never `absent`. The reverse — a real machine a tool holds with no managed device at a site NinjaOne manages — is `unmanaged`, one entry per machine carrying every vendor id, and the CSV writes one line per vendor record so same-named rows are never collapsed; one with a default Windows name (`DESKTOP-`, `LAPTOP-`, `WIN-` and random characters) is noted **likely not yet onboarded** (`core.NOT_ONBOARDED`, on the board, the CSV, the chat tools and the Devices page); a row a tool discovered rather than installed on (Bitdefender `isManaged: false`, ConnectSecure probes and deprecated agents) is `discovered`, reported apart; **a ConnectSecure row whose name is an IP address, or a dotted name with an address in it, is `external`** — a scan target on the outside of the network, reported apart and never an unmanaged endpoint (`core.external_target`; the address is the test, not the words around it: a rule on ISP pool labels flagged two of the pilot's own workstations and was dropped); an endpoint at a site with no NinjaOne mapping is not assessable and not shown as unmanaged. The population of a site with two organisations on a tool is their union.
- **A vendor that did not answer is not assessed this run, never absent and never unmanaged**, on every path. On the board a tool whose listing failed or timed out is `not_assessed` for every device with the reason on its `ToolReport`; a failed last-seen read leaves the lost devices it was for `not_assessed`, neither lost nor alive, their rows still claimed (`assess(..., undated_tools=)`); a NinjaOne MAC or serial query that failed makes every tool `not_assessed`, because the passes would pair less and report the difference as gaps. The resolution makes, moves and deactivates no link for a tool that did not answer, runs no passes at all when a NinjaOne key query failed, and leaves a lost device's status as it was when it cannot be decided. The review records a gap and keeps the facts it has. A day like that is a gap in the trend, not a day the fleet got worse; `tests/api/test_vendor_failures.py` simulates each timeout at the HTTP layer. Timeouts are per connector: `<CONNECTOR>_TIMEOUT_SECONDS` overrides `CONNECTOR_TIMEOUT_SECONDS` for one vendor (`Settings.connector_timeout_for`), and Bitdefender defaults to 120 because its inventory pages took 27 to 90 seconds live.
- **Backup is the one tool here that is sold per machine, so the site's backup scope applies to this board too** (`app/coverage/scope.py`). Every other tool is rolled out to a fleet: a managed computer either has a protection agent or it is a gap. A customer who backs up their servers and not their laptops has no gap on those laptops, and a board that counts them tells them the same wrong thing every month — live, the pilot's Backup column read 5.4%, which was the share of their fleet that happens to be servers. The rule is `effective_scope`, the one the review's gap list and the ticket panel already apply, so the four readers cannot come to two views of one laptop. A machine outside its site's scope with no Cove device is `not_in_scope`: out of the percentage, counted on its own line ("12 not in backup scope"), never a gap. A machine outside the scope that Cove *does* hold keeps its verdict — being backed up ends the argument about whether it should be — and `excluded`, `not_assessed` and the RMM's own states are untouched, because each already says something this does not contradict. Server or workstation is `device_role` given the node class alone, since the board's population is the device listing and the OS name is a second tenant read it does not make; the one disagreement that allows is the conservative one (a Windows 10 IoT till classed `WINDOWS_SERVER` stays in scope and stays a gap). The pass is skipped entirely when Cove did not answer, so a board computed without a database still gives the same answer.
- **An exclusion is a decision with a reason, a name and a time**, never a deletion. The reason is required by the API model, the service and a database check constraint; the device shows as `excluded` with the reason and never leaves the board; withdrawing is a second write on the same row; both are `coverage_excluded` audit rows. Franchisee admins and Inputiv staff exclude (`CAN_MANAGE_COVERAGE`); viewers read.
- **A board key is not a connector name, and `app/coverage/naming.py` is the only place either becomes the other.** An entry is named for what it measures and a vendor record is keyed by the connector that wrote it; for GravityZone and ConnectSecure the two words are the same, which is why nothing enforced the difference until Backup arrived reading Cove — and then the same confusion was written five times: links keyed by the board key so every Cove record looked new each run, two comparisons in the identity reader that matched nothing and reported 0% coverage where Cove held a device for every machine, a `ConnectorName("backup")` that raises, and a Devices column asserting a gap on a tool a customer does not own. `connector_of`, `connector_name_of` and `board_key_of` are the translations; `tests/coverage/test_naming.py` proves the hazard is real and fails on the shapes those five were written in, so the sixth is caught in review.
- **The diagnostic sits beside the join and never in it** (`diagnose.py`, `scripts/coverage_diagnose.py`). For every gap it says what would have paired it — the same hostname at another site (a mapping problem; both sites named), a normalisation the join does not apply (the field or rule named), a MAC or serial at the same site (the key named), or nothing — splits unmanaged endpoints into not assessable, discovered and real, reports RMM-stale devices apart from absent, and prints the legacy audit's tenant-wide match rate beside the board's. It changes no board number: a rule is adopted into the join only with the counts that justify it (validation log, 2026-09-24).
- **The page never computes.** The board is stored whole with each snapshot (`coverage_snapshots.board`, `serialize.report_to_json`), computed *without* exclusions; the page and its API (`/coverage/board`, a site, the CSV) read the latest row (`snapshots.latest_snapshot`), lay the client's live exclusions over it (`report_from_json`), and say when it was taken and by whom. An exclusion made after the snapshot shows at once, no vendor call. A client with no snapshot yet gets an empty board that says so, not a computation. **Refresh** (`POST /coverage/refresh`, franchisee admins and Inputiv staff) runs `take_snapshot` as a background task, one at a time per client (`refresh.REFRESHES`, single-flight: a second request joins the running one); the page polls `GET /coverage/refresh` and reloads when it lands, and a failure is shown on the page, never raised at it. The daily collector writes the same rows (`--no-coverage` / `--coverage-only`), one per (client, day), replaced on a rerun; the trend and "new gaps since the snapshot before" are read from the rows. **The page says how old the board is, in words, and not only when it was taken.** `COVERAGE_BOARD_STALE_DAYS` (2, the collector's own cadence plus one) is the line: past it the age is a dot and a word with the server's definition beside it, as every ticket statistic carries its own. A date alone is not enough — a snapshot nineteen days old sat on the demo tenant's page reading "Board as of 1 Oct" and reporting 0% endpoint protection and 0% vulnerability scanning at every site, while the Devices page, reading the links the daily resolution writes, had the same machines covered by both tools. Neither page was wrong about what it read; the board was computed before the matching worked on that world and nobody had recomputed it. Recomputed, it is 96.8% and 96.7%, and unmanaged endpoints fall from 492 to 12. A cold computation is three tenant listings, two NinjaOne queries, the last-seen reads for the lost pairings and a join run twice (live, 2026-09-28: 50 to 120 s on a slow GravityZone day, of which the listing is most); a page load is a database read.

## Device identity

`app/devices/` is the join, remembered. A `Device` is one machine at one site (canonical name, NetBIOS key, serials, MACs, class, OS, status, first and last seen); a `DeviceVendorLink` is one vendor's record of it (connector, the vendor's id, `matched_by`, first and last seen, active), several per connector allowed because a vendor holds several rows for one machine. The whole layer sits behind `DEVICE_IDENTITY_ENABLED`, **default off, and the default is not changed without a live agreement run**; off, nothing reads or writes it except the daily job and the scripts.

- **Resolution is the coverage join, written down** (`resolve.py`, run by the daily collector before the coverage snapshot, `--no-devices` to skip, or `scripts/devices.py resolve`). NinjaOne's computers are devices; then each tool's inventory runs through `core.assess` — the same four one-to-one passes within the site, twins told apart by MAC or serial — and every pairing becomes a link carrying its pass, every record no pass placed becomes a device of its own with a `vendor_only` link (or joins the vendor-only device that already carries its exact name at the site), a record with more than one candidate goes to the **unresolved queue** with the candidates named and the pass (`found_by`), never paired with the nearest, and an external scan target becomes nothing. **The passes are fed exactly what the board's are, or the two drift**: the population is the devices NinjaOne returned this run under their `hostname`, with NinjaOne's MACs, serial and last contact, a lost device taking part as it does on the board (its status is `rmm_agent_down` when a linked row is alive by the same last-seen read); a device made from another vendor's record is never a candidate, or the result would depend on which tool ran first; and every record goes in, linked or not, so a device an exact pairing takes is not free for a weaker pass to give to a second row. A `vendor_only` link is the absence of a pairing, remembered, and is offered to the passes again every run: when the pass places it the same row moves to the managed device (`links_moved`) and the device it leaves retires in time. A link a pass made stands even when the join later finds the record ambiguous — the queue is for records with no standing link — and a manual one always stands; the agreement script reports the day that makes a difference. Otherwise the job is idempotent: a link is keyed by `(connector, vendor id)`, a rerun creates nothing and touches `last_seen_at`; a record the vendor no longer returns leaves its link inactive (a tool that did not answer changes nothing); a device NinjaOne has not heard from past `COVERAGE_RMM_STALE_DAYS` is `rmm_stale` or `rmm_agent_down` (migration 0017), one no vendor has returned for `DEVICE_RETIRE_DAYS` (90) is `retired`. **Nothing is ever deleted.** Each run is a `devices_resolved` audit row with the counts.
- **A person corrects it, with a reason** (`admin.py`, `scripts/devices.py link | unlink | unresolved | show`, and the Devices page). `link` ties a record to a device by hand (`matched_by = manual`, which the job then leaves alone) and refuses a record active on another device; `unlink` needs a reason, keeps the row inactive with it and queues the record again (a record has one queue row ever, reopened rather than doubled). Both are `device_linked` audit rows naming the user when there is one. The terminal gets device ids, vendor ids, link ids, passes and dates, never a hostname.
- **The Devices page is the layer on screen** (`app/api/devices.py`, `templates/devices.html`, `static/js/devices.js`), scoped from the session like every page. Every role reads the list — one row per machine per site, its status, which vendors hold an active record of it and when each last returned one, filtered by site, status and "missing from" a vendor, with a CSV under the same filters — and a device: its links with `matched_by` on each, then what NinjaOne, Bitdefender and ConnectSecure say and the Autotask tickets that mention it in ninety days, read through `get_device`, `get_endpoint_protection`, `get_asset_vulnerabilities` and `search_tickets`, each asked by the name that vendor's own link carries and each a `tool_call` audit row; a vendor with no active link is not asked, and one that errors shows the error. The unresolved queue with its candidate devices, the link and unlink actions (a reason required; 422 without one, 404 for another client's device or link, 409 for a record active on another device) and the day's agreement are Inputiv staff only (`INPUTIV_ANY`), because a link changes coverage numbers a franchisee reads; a franchisee is shown neither card and the endpoints refuse them. The page reads the tables as of the last resolution and says when that was, flag on or off; the flag decides only what the board and the tools read.
- **Flag on, the readers resolve through the links and their contracts do not change** (`identity.py`). The board reads `assess_from_identity`, which returns the same `Assessment` from stored links instead of the inline join, and keeps the join's two refusals — a device with no hostname is `unmatched` whatever the links say, and so is one of two managed devices sharing a hostname while the tool holds a row of that name nobody has, unless a person linked the record by hand or a pass that tells twins apart (MAC, serial) made the link, since a name pass cannot have (`core.NAME_PASSES`); the review's coverage and scan-coverage derivations read the paired names the collector loads from the links, under the same refusals, and keep same-named vendor rows as rows (`security.record_rows`) so the review's join sees what the board's sees; `get_device`, `get_endpoint_protection` and `get_asset_vulnerabilities` reach, besides the name matches they always made, the records linked to the devices of that name (`lookup.linked_ids`), so a MAC-paired endpoint under an old name is found. Same arguments, same answer shapes.
- **The two paths must agree, and a difference is a finding.** `tests/api/test_devices.py` computes the board and a review's coverage facts flag off and on against the recorded inventories and asserts identical per-site counts; `scripts/devices_agreement.py` does the same live, board and one named site, and prints every differing count rather than reconciling it (live, 2026-09-24: 58 sites identical, the pilot's review identical; 2026-09-28, after the matching changes: 58 sites identical, Austin Tax Advisors' review identical). The daily collector does the board half every day after the resolution and the snapshot (`agreement.py`: `compare`, `run_agreement`) and keeps the answer as a `device_agreements` row, differences and all; the Devices page shows Inputiv staff the latest, naming the differing sites. Two gaps are expected and neither is reconciled in code: time — the links are as of the last resolution and the join of the cached inventories, so run the resolution first — and memory, a pairing a pass made that the join later finds ambiguous, which stands until a person unlinks it.

## Ticket workspace

`app/tickets/` is one Autotask ticket worked on a page: the machine it concerns, what every tool says about that machine, and a remediation plan an engineer reviews. **Read-only to every vendor; what is written is ours** (`ticket_workspaces`, `ticket_plans`). Inputiv staff and a franchisee's administrator open workspaces and generate plans (`CAN_CHAT`: the roles that may make the engine call a model); a viewer has no nav entry and is refused. Scoped from the session like everything else; another client's workspace or plan is a 404. Every vendor read is a `tool_call` audit row; every generation, device choice, review and outcome is its own event. The rules:

- **A ticket's text is scrubbed before it is stored or shown to a model** (`scrub.py`): values after password, passphrase, PIN, secret, token, API-key and BitLocker-key words; `Bearer` and `Basic` values; PEM blocks; the well-known key shapes (AWS, GitHub, Slack, Anthropic, OpenAI, JWT); any 32-plus run of key-looking characters. Hostnames, users, IPs, ticket numbers and error codes stay, because an engineer needs them. The workspace stores how many were removed and the page says so. Nothing ever holds the raw text.
- **The machine is found through the identity layer, with the method and confidence shown, and never guessed** (`resolve.py`). Hostname-looking tokens in the title and description are looked up against the ticket's site's devices: an exact canonical name is `high`, a NetBIOS key or another vendor's name for the machine `medium`. Then the contact against NinjaOne's last logged-on user per device at the site, on the usual login shapes: one machine `medium`, several `low` each. The device is chosen for the engineer only when one candidate stands above the rest; otherwise the candidates are listed and the engineer chooses (or says the ticket is about no machine), which is method `engineer` at `high`, recorded with a note and a `ticket_device_chosen` row, and stands across reopenings. Live, first three tickets: one by hostname at high, one with two low contact candidates left to the engineer, one with none.
- **The facts panel is computed in code, as of a time, and refreshed on request** (`enrich.py`): NinjaOne state, last contact, pending reboot, low disks; open alerts on the device; Bitdefender agent, signatures, modules, infection, isolation; ConnectSecure confirmed critical and known-exploited counts, scan date, grade; Cove backup; failed patch installs in `TICKET_RECENT_DAYS`; other tickets for the device and from the contact. Each vendor is asked by the name its own link carries; a machine with no NinjaOne link is not asked of NinjaOne, and that is the fact. A tool that errors is an error entry, never a blank. Each fact has a stable id a plan can cite.
- **Backup on the panel is one read and the review's own rules.** One read of the customer's Cove rows: the machine comes out of it by the name its *link* carries and never by a name join of our own — the coverage gap has one join — and the rest of the rows decide an `auto` scope. Four readings where there is a record (`backup.status`, days since a successful backup, the last successful one, failures in `BACKUP_RECENT_DAYS` (7) — a week, because on a ticket the question is whether somebody has seen this before, not what the month came to), and where there is none, **the site's backup scope decides which absence it is**: `effective_scope`, the same rule the review's gap list applies, so a workstation at a customer who backs up servers only reads `not_in_scope` with the rule that applied, not a red `not_backed_up`. A customer with no Cove at all is `backup.not_assessed`, decided before the read as the Microsoft 365 block is. The word is `status_of`'s, so a machine reads the same here as in a review, and the findings (`backup_none`, `backup_failed`, `backup_repeat_failures`) are built from `backup.status` and nothing else.
- **The contact gets an Account block of their own, under the machine's readings**: the Microsoft 365 account behind the address Autotask holds for them — enabled, MFA registered with the methods, days since a sign-in with the date beneath it, the licences, and two readings that appear only when they are the exception (a mailbox that is not a person's, a member account with nothing assigned). **Matched by email and nothing looser**, which is why `TicketWorkspace.contact_email` exists (migration 0034): a name matches several people in a directory. The sign-in reading is a *count of days* rather than a timestamp, because that is what a finding is made of and a shadow snapshot keeps a number and drops a string. A customer with no Microsoft 365 is **not assessed** — the coverage board's rule on one panel — decided before the read is audited (`factory.why_not_configured`), so an absence is never reported as a failed read. The block is part of the readings and is gated exactly as they are: a franchisee administrator and technician see it, a viewer sees no workspace at all.
- **A plan is steps that cite, or nothing** (`plan.py`). Evidence is gathered in code: resolved tickets `search_tickets` finds for the title and its two rarest words (their scrubbed description and resolution, whole client), the enrichment facts, and � first � steps an engineer marked as having resolved a similar ticket. The model may also web-search vendor documentation on `TICKET_WEB_SEARCH_ALLOWED_DOMAINS` (never empty; the URL is checked in code as well), and **never with client data in a query**: the queries are checked against the client, site, device, contact and every hostname seen, and a leak voids every web citation in that plan and is recorded. Every step must cite `ticket:`, `fact:`, `resolved:` or a `url:` the searches returned; a step that cites nothing we hold is dropped and counted, never shown (live: 5 of 8 on one plan, from URLs the model retyped, before the match was loosened to host and path). A command appears only when it is in a cited ticket's text word for word (`command_source`); an invented one is removed, code in the prose that no source holds is replaced with a marker, and a command from the web is never shown as a command because we do not hold the page. Every step is marked "manual, not executed" or "command from <ticket>, not executed": nothing here executes anything. Text instead of the plan tool, or an empty plan, gets one last turn with the tool required and search off.
- **Plans are versioned per ticket with the author, never overwritten.** Each generation is version n+1 with who asked; an engineer accepts, edits (the new wording kept beside the original) or rejects each step of the latest version, each a `ticket_plan_reviewed` row. The prompt, each search and the model's answer are `prompt`, `web_search` and `model_response` rows; the plan is `ticket_plan_generated` with steps kept, dropped and citations.
- **The figures above the queue are one read-only endpoint, cached** (`statistics.py`, `GET /tickets/statistics`, `CAN_CHAT` like the rest). Two Autotask listings and nothing else: every open ticket, and every ticket completed inside the window. Two cover the whole window because a ticket created inside it is either still open or was completed after it was created and therefore inside it too — there is no third case and so no third read. **Every figure carries its own definition in the payload**, beside the number, because a definition written on the page and a figure computed on the server drift; that is the review's fact rule applied to a dashboard. The answer is kept per client for `TICKET_STATISTICS_TTL_SECONDS` (300) behind a per-client lock, in memory and therefore per process — written down rather than hidden, like the sign-in rate limit — and every response says when it was worked out and whether it came from the cache. **A card is the filter it describes**: `CARD_FILTERS` names the queue's own chips, and a test asserts no card points at a filter the page does not implement, because that is exactly how a figure and the rows it opens become two different populations. Days are counted in the franchisee's own `business_hours.timezone` where one is set and UTC where none is, and the definition names which; the boundary instants are in the payload so the page filters against the same midnight the server counted from. Resolved-this-week tickets are closed and so are not in the open queue: that card opens them as their own list, capped with the count left uncapped and the cap stated.
- **The loop closes when the ticket does** (`workspace.py`). Polling (`POST /tickets/poll`, the page's button, `scripts/tickets.py poll`) asks Autotask about every open workspace with a plan and stamps `closed_at`; the page then prompts the plan's author (or the workspace's opener) to say which steps resolved it, or that none did, with a note. The answer is stored on the plan (`ticket_outcome_recorded`) and those steps are evidence ranked first the next time a similar ticket comes in.
- **Live, 2026-09-25, three open pilot tickets**: 3, 8 and 10 steps kept, 3, 11 and 17 citations, 45 to 132 seconds a plan, most of it the model's two web searches and six `get_ticket` reads for the evidence (validation log). Two things the run surfaced and left open: a site holding two GravityZone companies fails a site-scoped `getNetworkInventoryItems` on one of them (`Invalid value for 'parentId'`), so Bitdefender facts for such a site error until that is fixed in the connector; and Autotask configuration items return 500 for this tenant, so the device's ticket history falls back to the text search.

## Resolved: clocks, ledger, baselines

`app/resolved/` is the read-only foundation of the per-outcome service: what a ticket's targets were, what actually happened to it, and what that costs today. It reads Autotask through the same factory as everything else (hard rules 1 and 5), writes nothing to any vendor, and audits every read (hard rule 4). Nothing here is a constant: every target, class, resolver and rate is one franchisee's setting.

**Settings live with the franchisee's other settings** (`config.py`, composed into `FranchiseeConfig` as `resolved`, so one `report_configs` row per client). The business hours an SLA clock runs on are the ones the business review already uses: two places to set a franchisee's working week is one too many. **Everything is stored as a label, never as a picklist number** — Autotask's status, priority, queue and issue-type numbers mean different things in different databases, so a config saying `status = 7` would be quietly wrong on the next tenant. Numbers are resolved to labels through the tenant's own `entityInformation/fields` and matched case-insensitively. Set with `manage_client.py report-config`; `ResolvedConfig.configured` is false until somebody does, and an unconfigured franchisee gets "no target" everywhere rather than a default nobody agreed to.

**The definitions, in full, because they are what the service is sold against** (`sla.py`, whose module docstring is the same text):

- *First response.* Working minutes from the moment Autotask stamped the ticket created to the moment it stamped a first response; a ticket with no response yet is measured to now. Met when the minutes used are at or under that priority's target.
- *Resolution.* Working minutes from created to the completed date Autotask stamped; a ticket not completed is measured to now.
- *Working minutes* are the franchisee's `business_hours` — days, start, end — in their own time zone, minus their holidays. The clock **walks local days rather than subtracting two instants**, so a span across a daylight-saving change is still two working days of eight hours (`clock.py`; `tests/resolved/test_clock.py` asserts it over 1 November 2026). A franchisee on a 24/7 agreement sets `clock = "calendar"` and everything counts. A deadline that never lands — a target longer than the open days remaining inside `MAX_DAYS` — is no due time rather than an invented one.
- *Paused.* A ticket whose **current** status is one the franchisee named as pausing (waiting customer, waiting vendor) has its clock stopped. **Autotask exposes no status history we read**, so we know that a ticket is paused now and never how long it has been: a paused clock is reported `paused` and **no breach is asserted from it**. That is a deliberate under-count, documented rather than hidden, and it is why paused tickets are counted on their own card instead of being folded into the breach figure. The one thing pausing cannot do is undo a clock that has already run out: a target used up before the ticket was parked is a breach that happened.
- *No target.* A priority the settings do not name, with no default, is reported `no_target` and left out of every percentage — never met, which would flatter, and never breached, which would be a number nobody could defend.
- The word on a queue row is the **worse of the two live clocks**: `breached`, `due_soon` (inside `DUE_SOON`, 24 hours), `ok`, `paused` or `none`. A clock that has stopped is history and does not decide what the row says now — a ticket answered late but still open shows where its resolution clock stands, with the missed response in the detail and still counted as missed in every percentage taken later.

**Autotask's own SLA fields are not read anywhere.** `serviceLevelAgreementHasBeenMet` is populated on none of the pilot's tickets, `firstResponseDueDateTime` on about two thirds and `resolvedDueDateTime` on a third, so a breach count drawn from them counts the tickets somebody remembered to configure at the vendor. **Every breach figure in the product now comes from this calculation**: the Tickets page and its statistics endpoint, the `list_sla_breaches` tool, and the business review's service facts (which skip a clock whose verdict is `None`, so paused and untargeted tickets are in neither numerator nor denominator).

**The outcome ledger is one row per completed ticket** (`ledger.py`, `ticket_outcomes`, migration 0022), filled by the daily collector and backfillable with `resolved.py ledger --days N`. Each row carries the franchisee, the site, the ticket id and number, the class, the resolver's side, created / first response / completed, business-hours minutes to pickup and to resolve, whether each clock was met (nullable: **not judged is not the same as not met**), hours logged and cost, whether it reopened and when, and a link to any ticket-workspace plan with the outcome an engineer recorded on it. **Idempotent**: keyed `(client_id, ticket_id)` and written with an upsert, so a rerun changes nothing. **A ticket that came back updates its row** rather than gaining a second: the run also reads the open tickets we already hold a completed row for — **only those completed inside `reopened_within_days`**, because the mark is decided by that same window, so a ticket completed before it cannot earn one however it is read, and because the alternative is an `in` filter that grows with the table for ever (2,721 ids after one backfill, which is what first breached Autotask's condition limit); a ticket open again within the window is marked reopened; a later completion overwrites the times and keeps the mark, so the ledger says both that it closed and that it did not stay closed. Class comes from `ClassificationConfig` (ordered rules over priority, queue and issue type, first match wins, then a default), the resolver's side from a per-franchisee list of the names, logins and addresses Inputiv's people are known by at that tenant (`inputiv`, `franchisee`, or **`unknown` when nobody was assigned** — never quietly given to a side), and cost from hours logged at each engineer's loaded hourly rate. Ticket titles are scrubbed before they are stored, as the workspace scrubs them.

**Baselines are read from Autotask, not from the ledger** (`baselines.py`, `resolved.py baseline --days N`), so a range predating the ledger still answers — and computed by the same classification, clock and cost book, so the two can never disagree about a ticket they both hold. Median and 90th percentile working minutes to pickup and to resolve, by class, with cost per ticket. **A percentile names a real ticket**: nearest rank, not an interpolation between two of them. Every figure says how many tickets it was measured over, and the caller decides whether a percentile over nine tickets is a baseline. A class nobody logged time against gets no cost rather than a zero, and a franchisee with no cost book gets no money anywhere: a figure from a guessed hourly rate is worse than no figure. Money is rounded where it is rendered, never carried as a float.

## Autopilot

`app/autopilot/` is the agent doing triage, one level of autonomy at a time. **Level 0 is shadow mode: it predicts, it is scored, and it writes nothing anywhere but our own tables.** The order is deliberate — nothing is allowed to act until there is a number saying how often it would have been right — and the rules below are what make that number worth reading.

- **The shadow package cannot reach a vendor, structurally.** Nothing under `app/autopilot/shadow/` imports `app/connectors/factory.py`, a vendor client, or anything that reaches one (`app.resolved.ledger`, `app.tickets.enrich`); `tests/autopilot/test_imports.py` checks the package's own imports *and* the real import graph in a subprocess, so an indirect reach three hops down fails the suite. The forward shadow's live reads are injected from `app/autopilot/wiring.py`, which is the one place the two meet.
- **A replay runs on stored rows.** Part A reads `ticket_outcomes` and calls no vendor at all, so measuring the agent costs a franchisee's tenant nothing and cannot be mistaken for doing something to it. It therefore covers **completed tickets only** — the ledger is one row per completed ticket — so the replay population is resolved work and the forward shadow's will not be like it.
- **A number is read off the holdout, and a setting is chosen on the development period.** The window splits on creation time: the first stretch is where a label policy or a confidence threshold may be chosen, the last `--holdout-days` (30) are scored and otherwise left alone, measured back from the newest ticket so "the last thirty days" means of the data. A threshold chosen by looking at the tickets it is then scored on is a memory, not a measurement, and `shadow score` defaults to `--period holdout` so the honest number is the easy one to quote.
- **Coverage is reported beside every accuracy.** A threshold trades one for the other, and an agent that answers four tickets perfectly is not better than one that answers four hundred well. A threshold is modelled as what it is: everything below the floor becomes a decline, with the judgeable population staying the denominator.
- **A franchisee's label policy is a setting, applied after the model answers** (`app/autopilot/config.py`, stored with their other settings as `autopilot`). `forbidden_issue_types` are labels the agent may not predict — one that comes back becomes `unsure`, a decline — and `issue_type_remap` says which labels this franchisee files as something else. Both are copied onto every run's config, and the **raw** answer stays on the row beside the policy's verdict, so accuracy before and after a policy are two numbers from one run. `score --apply-policy` re-derives the answers from the raw labels, which is how a policy chosen on the development period is scored on the holdout without asking the model anything again. The pilot needed one: offered `Customer Onboarding Offboarding`, which they filed nine tickets under in ninety days, the agent reached for it 219 times — 18% of every wrong answer.
- **A run is committed in batches, watchable and resumable.** Every `--batch` tickets (100), with progress printed; `--resume <run id>` answers only the tickets that run has no prediction for, and grouping still walks every ticket in creation order so a resumed run forms the same groups as an uninterrupted one. The first full replay held one transaction for nine minutes, which meant nothing visible from another connection and nothing kept if it were interrupted.
- **Cached input is counted apart from input.** It is billed at a fraction, and a replay reads the same instructions once per ticket, so folding the two together overstated the cost several-fold. Unset, `AUTOPILOT_CACHE_READ_COST_PER_MTOK` prices cached reads at the input rate, which errs towards overstating — the right direction for a cap and the wrong one for a quote.
- **The agent sees only what was known when the ticket arrived**: the scrubbed subject, a per-customer handle and the arrival time. Withheld: issue type, sub-issue type, priority, status, assignee, resolver, hours, every duration and every outcome. **The queue is withheld too** — the ledger reads it at completion and `Escalation` is where a ticket is *sent*, so including it would let what happened leak into what was known. It is available as the `with_alert_queue` variant so its worth is measured rather than assumed, and the variant is on the run's config.
- **Grouping looks backwards only.** Tickets are walked in creation order and a ticket may join an earlier one and never a later one, within one site, on title similarity. Deterministic and not a model call, so a replay cannot see the future and a number that moves moved because the window or the threshold moved — both on the run's config.
- **Predictions are a closed set, and an invalid answer is recorded rather than repaired.** `origin`, `issue_type`, `urgency` and a confidence each; `issue_type` must be one of *that tenant's* labels or `unsure`. A label the tenant does not have, a confidence out of range, a missing or invented field, the right label in the wrong case, or text where a tool call was required all become an error row. Nothing is nearest-matched, clamped or defaulted: code that tidies the model's output turns a measurement of the agent into a measurement of our tidying up. **A ticket's words are data and can never change which fields or values come back** — the schema is built from the tenant's labels, so the worst a hostile subject achieves is being classified oddly.
- **`unsure` is a decline, not an error**, and is out of the accuracy denominator. Finding where the agent should stay quiet is the point of Level 0, and folding declines into the error rate pushes the threshold the wrong way.
- **No ticket text in any shadow table.** Not a title, not an excerpt, not a reason quoting one. `shadow_predictions` is ids, labels, numbers and timing; a `shadow_enrichments` fact keeps its value only where it is a number, a flag or a time, and a string is treated as a name and dropped. The two files that do carry titles — the 200-ticket origin labelling sheet and the 30-group spot-check — go to `var/`, git-ignored, as working papers for a person.
- **A run records what it ran as**: the commit, the model (`AUTOPILOT_MODEL`, falling back to `ANTHROPIC_MODEL`), the prompt version and the config. Two runs whose numbers differ are only informative if what changed between them is known.
- **Cheap paths first.** Rules answer where a machine's wording is unmistakable and the model answers the rest; the two are scored apart so the rules have to earn their place, each names itself on its rows, and a rule asserts a tenant's issue type only where that tenant has the label. Live, 2026-10-01: the rule path was 100% accurate on 158 judged tickets and the model path 60.3%.
- **Iterating runs on a fixed sample; the number that goes in front of anybody comes from a full replay.** A full replay of the pilot's ninety days is 2,722 tickets and 5.2M tokens, and almost none of that answers the question somebody asks a dozen times a day — did that change help. `shadow sample` draws ~600 once, stratified by issue type across both periods, splitting where scoring splits, and **stores** it (`shadow_samples`, migration 0027): drawn again from a seed per run it would move the moment the ledger gained a row, and two runs would stop being comparable without anybody touching anything. `shadow replay` uses it by default and `--full` replays the window, that way round because the costs differ by a factor of four and the command people reach for all day should be the cheap one. Grouping still walks every ticket in the window in creation order, because a walk with gaps forms different groups; only the classifying is narrowed. A run records which sample it used, and an untyped ticket is in no sample — there is no class to stratify it under and nothing for its issue type to be scored against.
- **A question already answered is not asked again.** Every prediction carries `input_hash`, the digest of exactly what was sent — model, instructions, the tenant's label set, the tool schema, the ticket's line — built in one place with the request so the two cannot drift (migration 0028). A run reads a stored answer when ticket, digest, model and prompt version all match, and records `reused_from_run_id`. Nothing is matched loosely: a cheaper reuse that answers a different question is a wrong number, not a saving. What follows is the point of it — **a label policy, a threshold or a sample redraw costs no model calls at all**, because all three are applied after the model has answered, and the alert-queue variant costs calls only for the alert-shaped tickets whose input it changes. An error is asked again rather than inherited.
- **A replay may go through the Message Batches API** (`AUTOPILOT_BATCH_REPLAY`, `--batched`, off by default): about half the price, answered within hours. The batch is written down at submission (`shadow_batches`, migration 0029) and running the same command again either says where it is or collects it, so a batch id is never left in a terminal somebody closes. A batch result is read by the same function as a request's message — a batch is a cheaper way to ask, not a different measurement — and its three non-message outcomes become error rows. **The live paths never use it**: the forward shadow, the backfill and the ticket card answer about a ticket an engineer is looking at now.
- **The answer is six values and nothing else** (prompt `shadow-v2`). The schema never had a free-text field; the prompt now says the tool call is the whole answer, and an ambiguous subject gets a low confidence rather than a sentence. Measured, that changed nothing — 173.6 output tokens a call before, 174.0 after — because about 131 of those tokens are fixed tool-call framing and 42 are the JSON. Two-character property names would save ~20 a call, 2% of a run, and are not worth an unreadable schema (validation log, 2026-10-02).
- **The model is a per-run flag** (`--model`, defaulting to `AUTOPILOT_MODEL`), so comparing two is two runs over one sample. Measured on the pilot's 600: Haiku is 6 to 7 points worse on issue type, its confidence separates less (82.7% at 0.90 against 94.3%), it is better on urgency, which is never gated — and it read **nothing** from the prompt cache, paying 1,736 input tokens a call against Sonnet's 399 plus 1,577 cached, because the instructions clear one model's caching minimum and not the other's. A cheaper model is not the same claim as a cheaper run.
- **Caps are settings and the one that always bites is on tokens.** The two per-million-token prices have no default, so an unpriced run reports tokens and says so rather than reporting zero — the review's price-book rule applied to model spend. A run stops cleanly on either cap and the run row says which.
- **Ground truth is named for what it is.** `issue_type` is scored against the stored label. `urgency` is scored against the *final* priority mapped to three bands, labelled approximate everywhere because priority moves after creation and we keep only the last value, and **reported but never gated**. `origin` has no stored truth at all — the vendor's own `source` field would be it and the ledger does not keep it — so it is scored against a labelled sample, with **two proxies** reported until that sheet comes back and both printed as proxies: a ticket nobody was ever assigned, and a ticket raised into an alert-shaped queue. Grouping has no truth either: counts, plus 30 groups for a person. Accuracy is also reported **by title length** (three words or fewer, four to six, seven plus), because a quarter of this tenant's subjects are three words and that is a different task from classifying a sentence.
- **Level 0 writes nothing to a vendor and neither does Level 1 without a new decision.** The forward shadow (`AUTOPILOT_SHADOW_LIVE`, false by default, refusing outright when false) polls for new tickets under a request budget we count ourselves, backs off on anything that is not an answer, and logs the full status, response headers and a bounded body of every refusal — because what Autotask's own threshold returns is still an open api-notes question. Enrichment is the ticket workspace's `resolve_device` and `enrich`, called as the page calls them, so there is never a second enrichment path to drift; configuration items stay unused (they 500 for the pilot tenant); Blackpoint is named on every snapshot as not built, because a tool nobody asked is a gap in the evidence and not a clean bill of health, while Cove moved onto `LIVE_CONNECTORS` when its connector landed and a customer who has none is carried by the enrichment's own `backup.not_assessed` reading — "not set up for this customer" is a different claim from "Desk cannot ask". The ticket's site and the device's site are both stored so "zero wrong-site enrichments" is a number somebody can check. Two facts a replay cannot have are recorded there: the **queue as read at arrival**, which at that moment says where the ticket was raised rather than where it was sent, and `has_description` — the scrubbed body goes to the model in flight and into no table, but whether there was one decides whether the two populations may be compared at all.
- **The gate is a panel with three verdicts, and "not measured" is one of them.** `app/autopilot/gate.py` holds the criteria and their targets: issue type at or above 85% on the holdout at the chosen threshold with at least 40% of holdout tickets answered, origin precision on `alert` at or above 95% against the **labelled sample and never a proxy**, 90% of sampled groups judged one thing, and a fortnight of forward shadow with no wrong-site enrichment. Urgency is reported and not gated. A criterion with no evidence yet is `not_measured` and says what is missing — not a fail, which would say the agent did badly at something nobody asked it, and not a pass, which would ship on nothing. **The two accuracy criteria are read against blind answers** — the past-ticket sample and the live quick checks together — and never against an approval or a proxy. The results page says "Ready for Level 1" or "Not ready yet" at the top, names the criterion that is stopping it and the next thing somebody would do about it, all three decided by the gate rather than by the page. **The threshold rule is fixed in advance and in settings**: the lowest development-period threshold where accuracy is at least `AUTOPILOT_THRESHOLD_MIN_ACCURACY` (88%) and coverage at least `AUTOPILOT_THRESHOLD_MIN_COVERAGE` (40%), copied onto every run's config, because a rule chosen after seeing the numbers chose a verdict once already.
- **Ground truth is a person's judgement, written down and never overwritten** (`app/models/labelling.py`, migration 0024, `app/autopilot/labelling.py`). A `labelling_sets` row is one sample of one run — the 200 origin tickets, stratified over issue types with a fixed seed, or that run's 30 groups — `labelling_items` is one thing to judge, and `labelling_answers` is what one person said about it once. **Answers are appended**: a change of mind is a new row, an undo is a row saying `withdrawn`, the latest row per labeller scores, and the rest is how a disputed label is looked into. `labeller_user_id` is `ON DELETE RESTRICT` like every other actor column. No ticket text is stored: an item is an id and a position, and the words are read from the ledger, scrubbed, at display time. A note a labeller writes is scrubbed on the way in, because somebody typing a note is as likely to paste a password as somebody typing a ticket. A fixed `AUTOPILOT_DOUBLE_LABEL_COUNT` (20) of the origin sample goes to a second labeller, and **a ticket two people label differently is left out of the scored labels** rather than settled by taking the newer or the senior answer: a label two people cannot agree on is not ground truth.
- **Two internal pages, Inputiv staff only** (`/autopilot/labelling` and `/autopilot/results`, `app/autopilot/api/`, nav group "Autopilot"). A franchisee gets 403 on both pages and on every endpoint and sees no nav entry: these are a measurement of our own agent, not something about their estate, so there is no friendlier page to send them to. **The labelling page judges blind** — the scrubbed title, the customer, the arrival time and the queue, with A / H / U to answer, S to skip, Z to undo and the arrows to move — and that is enforced by the payload rather than by the template: `TaskView` has no field for a prediction, a confidence or a ledger outcome to arrive in, and a test inspects the response's keys. **The results page is read only and provably so**: no POST, PUT, PATCH or DELETE exists under `/autopilot/results`, asserted on the router's own method list, and the forward shadow's switch is reported as a status naming `AUTOPILOT_SHADOW_LIVE` rather than offered as a toggle. Every figure carries the server's own definition beside it, the rule the ticket statistics follow. Both respect demo mode, where site names are pseudonyms, and every labelling write is an `autopilot_labelled` audit row whose payload says whether a note was written and never what it said.
- **The results page says which findings earn their place.** Under Live reviews, each kind with how often it was on a card and how often an engineer said it was worth the space: a kind shown four hundred times and marked useful twice is a line on four hundred cards nobody wanted. The counts are recomputed from the snapshots rather than stored, because a finding is a pure function of rows we keep.
- **The scoring reads those tables, not a spreadsheet.** `shadow score-origin` reads the stored labels and names its source; `--sheet` remains for the sheets filled in before the pages existed. `shadow score` prints the grouping spot-check from the same tables. Origin and grouping are read over the **whole run** — nothing is tuned on a hand label and the sample is drawn across the window — while the issue-type pair stays on the holdout, where the discipline is the point.
- **The card leads with what Autotask cannot see.** Kaseya Intelligence already suggests an issue type, a priority, a queue and an assignee from inside Autotask; repeating that is worth little. So the card on a ticket (`app/autopilot/findings.py`, `app/autopilot/api/suggestions.py`, migrations 0025 and 0026) opens with the estate — which machine, what the tools found, what to do about it — and puts the classification at the bottom as four compact lines. **A finding is ranked by how much it changes the handling**, not by how interesting it is: the machine is not there (nothing remote will work), and beside it the Microsoft 365 account being disabled (nothing they sign into will work either, and the machine is still said first); the ticket or alert is older than a week (it may not still apply); backup has failed; security, which is where no MFA registered sits; a repeat somebody has seen before; then the housekeeping, with a dormant account and an unlicensed one. A disabled account is not also called dormant, and MFA that could not be read is never reported as none: `None` is not "no". Four are shown and the rest are behind "Show N more", each with its glyph, its sentence, the qualifier after a middle dot, the tool that said so and the time it was read — a fact with no source is a claim. Two of those qualifiers are the point of the line: an alert raised before the machine went quiet says so, and out-of-date signatures on an offline machine say "expected while offline", because without it somebody chases a thing that cannot be true.
- **The suggested next step is written by rules from the findings, never by the model** — a suggestion nobody can trace is one nobody can check — and no rule matching means no section, because a bland line on every ticket is one people learn to skip.
- **Every row of the card is answerable and every answer is a row of ours.** A finding, the next step and the card as a whole are `useful` or `not_useful`; a classification is `correct`, `changed` or `wrong`, and Reject opens the franchisee's own labels in place. The two vocabularies do not mix, and the route refuses the crossings: "was this correct?" about "machine offline for 10 days" gets "yes, and I did not need telling". Verdicts live in `suggestion_reviews` with `field` as a classification name, `machine`, `next_step`, `card`, or `finding:<kind>` — a prefix rather than an enumeration, because the kinds are a vocabulary that grows and a new finding should not need a migration (0026). **Nothing is written to any vendor**: Copy to Autotask puts plain text on the clipboard in the card's own order and pasting it is a person's keystroke.
- **The queue shows one "Desk found" column**, the top two findings as chips and "+N" for the rest, with "Nothing to flag" where there are none, and filter pills that count: "All open", "Needs review", "⚠ Has warnings". Not the classification — Autotask's own list already shows a type beside every row, and a second one of ours is noise.
- **Approval is not accuracy, and the two are stored in different tables.** An engineer who has read "Looks like User Access and Management" and pressed Correct has agreed with the agent; counting that as accuracy would make the measurement improve as the agent got more persuasive. So `suggestion_reviews` is approval — reported as the Level 1 readiness rows, with a target column reading "reported, not gated" and no pass or fail — and `blind_checks` is measurement. On `AUTOPILOT_BLIND_RATE` of suggested tickets (0.2) the card asks the two questions first with the suggestions hidden, the engineer is never told which tickets those are, and **that answer is what the gate's issue-type accuracy and alert precision are read against**. Which tickets ask first is a hash of (client, ticket) decided when the suggestion is made and written down: a coin flipped per page load would show the questions, then the answers on a refresh. Both tables are append only and their actor columns RESTRICT, like every other judgement here.
- **The past-ticket sample asks the same two questions** and writes its type answers to the same `blind_checks` table, so the gate reads one population rather than two and somebody who has done both has learnt one interface. That page is off the nav on purpose: the review that scales happens on a ticket an engineer is working anyway, and the sample is a job you take on from the results page when a gate row says it is waiting on one.
- **The display threshold is not the gate's threshold** (`AUTOPILOT_DISPLAY_THRESHOLD`, 0.80). It decides what an engineer is offered and nothing else; the gate's floor is still the fixed rule, chosen on a replay's development period. The threshold in force is stored on every suggestion, so a figure counted later knows which bar the suggestions it counted had to clear, and lowering the setting does not retroactively promote what was already shown.
- **Suggestions on live tickets come from the forward shadow**, which still refuses to run unless `AUTOPILOT_SHADOW_LIVE` is true. Off, a live client's page says so by name — a sentence, not an empty card, because "nothing to say" and "nothing is running" are different things — while the demo tenant's suggestions come from a simulated pass and are always reviewable.
- **Nothing polls on its own.** There is no poller process, no scheduled job and no background task in the web service: `forward_pass` is called by `scripts/autopilot.py shadow forward --client <slug> --once` and by nothing else. A schedule is that command on a cron service, shaped like the daily collector's block in `render.yaml`, and is a decision somebody makes rather than something that starts itself. `--once` is the only mode there is, and the command says so when it is left off. A pass reads from the last forward run's start, or from `--since-hours` back (24) when the client has never had one.
- **`shadow backfill` is the open queue, once.** The same pipeline over every ticket that is open *now*, whenever it arrived, because that is what an engineer opens next: `--limit N`, `--ticket <number>` (repeatable), `--redo`, and `--dry-run`, which names the tickets and the vendor requests it would use and calls no model. It is **resumable by construction** — a ticket that already has a suggestion is skipped, so running it again carries on — and it spends the same hourly `RequestBudget` as polling, working out before it starts how many tickets that leaves room for (a run that stops mid-ticket leaves a prediction with no enrichment). Both commands share one backoff (`with_backoff`): any failure doubles the wait, the terminal is told, and the last failure is raised rather than swallowed, because a backfill that quietly returned nothing because Autotask was down would read as a client with nothing open. Both report tickets processed, suggestions above the display threshold, model tokens, Autotask requests spent and the enrichment's own tool reads.
- Suggested resolutions are **out of scope at Level 0**: they need scrubbed note bodies, and the scrubber covers titles and descriptions only.

## Automation

`app/automation/` is the engine that will one day apply a fixed, versioned workflow — a leaver's offboarding, say — to a client's tools, with a person's approval in front of every run. Today it applies one workflow, `practice`, to a table it owns, on the demo tenant only; the point of building it first is that the switch, the dry run, the approval, the audit, the failure, the resume and the undo are all proven before anything real uses them. `docs/automation-workflows.md` is the guide to writing one. The rules:

- **No AI anywhere on this path, structurally.** A workflow is steps written in code; no model is called, no value is generated. Nothing under `app/automation/` imports `app.agent`, `app.autopilot`, the Anthropic client, the connector factory or any vendor client, and `tests/automation/test_imports.py` checks the package's own imports *and* the live import graph in a subprocess, as the shadow guard does. The one place the engine and the autopilot meet is `app/autopilot/wiring.py`, which imports the engine, never the other way round.
- **No writes to any client tool, and no write-capable connector exists.** The practice workflow writes to `automation_practice_records`. When write access arrives it comes through this engine alone, via write clients used by nothing else (hard rule 2).
- **A step is a contract** (`definitions.py`): `precondition` (read only; the dry run and again before the action), `plan` (read only; what would change, in the approver's words), `before` (the state about to change), `action` (the one thing that writes; **idempotent for one (run, step)**, because a recovered worker runs it again), `verify` (read only; a step is `done` when it passes, never because the action returned; its facts are the step's after-state), `undo` (optional; a step without one is listed as not undoable before approval). Every step also carries the words for what it checks, does, confirms and undoes — required, because the workflow page prints them for the authoriser. A step may depend on one earlier step, enforced at definition and at run time.
- **One state machine, one writer** (`states.py`): drafted → dry_run_ready → awaiting_approval → approved → running → completed, or failed / partly_completed / cancelled / undone, plus approved → awaiting_approval when an approval lapses and failed → awaiting_approval for a fresh approval. `advance` is the only writer of `state` and refuses anything not in the table. The dry run runs every precondition and plan and changes nothing; execution is in order, stops at the first failure, never skips a failed step, resumes from it, and never repeats a completed one.
- **Every run passes the same controls, including the practice workflow's.** A per-client, per-workflow switch, off by default; a per-client kill switch that blocks new runs and pauses a running one between steps (the step in flight finishes); an approval that records the client's authoriser (name, method, and the time they said yes — defaulting to the moment it is recorded, never in the future and never before the dry run they said yes to; the audit row keeps both `approved_at` and `recorded_at`; the name must be on the client's approver list in `AutomationConfig`) and the approving engineer, who cannot be the engineer who started the run; the record is shaped (`authoriser_ref`, `approval_payload`) so emailed or Teams approval links add a value, not a migration. Every check, action, verification, undo, start and approval is an `automation_run` or `automation_step` audit row with before and after; every switch change is `automation_control`.
- **Runs execute in the background and survive a restart** (`runner.py`, `scripts/automation_worker.py`). Never in a web request. One run at a time per client, kept by a partial unique index rather than by a worker remembering. Each step is its own transaction, marked running and committed before the action, so a worker that dies leaves a row that says where; its lapsed lease is how the next worker knows, and it takes the run up from that step. A failure is recorded on a connection of its own.
- **Approvals expire.** `approval_expires_at` is approval plus the workflow's `approval_window` (24 hours for practice). The worker never starts a run past it; housekeeping puts such a run back to awaiting approval with the lapsed approval on the audit row. A failed run resumed later than the window after it stopped is refused a resume and sent for a fresh approval (`resubmit`), recorded the same way. Drafts and runs awaiting approval for more than 7 days are cancelled by the worker, on the record.
- **A resume re-checks.** A step tried again re-runs its own precondition and re-verifies the step it depends on before acting; a dependency that no longer holds stops the run with the reason rather than acting on a changed situation. The direct dependency, not the chain: a step further back may have been changed on purpose by a step in between.
- **Undo looks before it puts anything back.** In reverse order, within the undo window, each step's verify is run again and its facts compared with the after-state recorded when it was done. Anything different means somebody changed it since the run; the step is marked `changed` and left alone, the rest are still undone, and the run says which. An undo never overwrites a newer change — which is why a verify reports only the fields its step owns.
- **Triggers draft and nothing more** (`triggers.py`). A workflow declares what starts it: `manual` (the Automations page; without one it cannot be drafted by hand), `ticket` and `alert` (fixed conditions on queue, issue type, sub-issue type, source and a title that equals or contains a phrase — evaluated in code, no regex, values overridable per client in settings), and `schedule`. Ticket and alert rules read new tickets through `scripts/automation.py poll --client <slug> --once`, behind its own switch `AUTOMATION_TRIGGERS_LIVE` (false by default, separate from the shadow's): the same Autotask reader and hourly request budget as the forward shadow (`app/tickets/poller.py`, `app/tickets/arrivals.py`), the reader injected so the engine imports no connector, and no model anywhere — `tests/automation/test_imports.py` names the modules that can reach one and fails if the command imports any, and asserts the forward shadow imports nothing of the engine, so each feature has one owner. Each poll is an `automation_control` audit row (`control: poll`) the next poll reads its start from. A commented-out cron in `render.yaml` runs it every quarter hour (docs/deploy.md, 5b). A trigger drafts only when the workflow is allowed on the client, the workflow's switch and the trigger's own switch are both on, the kill switch is clear and no run of any state exists for that ticket and workflow (one draft per ticket per workflow, a unique index too). Every evaluation — matched, skipped and why, or which condition failed — is a row in the client's trigger log, the last hundred shown on the Automations page. Schedules, stale drafts and lapsed approvals are the worker's housekeeping between pieces of work.
- **A workflow is started by hand from the Automations page or from a ticket.** The ticket page's More menu offers staff "Start a workflow": the workflows that are on for this client and have a manual trigger (`GET /automation/startable`), one item each; choosing one drafts a run with the ticket attached and its inputs filled from the ticket where `input_sources` says how (`POST /automation/runs` with a `ticket`), and opens the run page. The group is left out of a franchisee's markup and the endpoints refuse them.
- **Four pages, Inputiv staff only** (`INPUTIV_ANY`; a franchisee gets 403 on every page and endpoint and no nav entry), and all of them are spare on purpose: no sentence on a main view explains how the system works (that is one "How this works" disclosure per page, five short lines at most), labels and buttons are three words or fewer, a status is shown only where it is the exception ("Can't be undone" on the step that cannot, nothing on the others), no internal name — a key, a field, a picklist value — reaches the screen, and a dialog is a question, at most one short sentence and two buttons. Automations: subtitle client · "3 of 7 on" · Paused only when paused; tabs Workflows · Runs · Notes; one row per workflow with its name, one line saying what starts it ("When a disk space alert arrives."), a dot and a word (Off / On / Review first / Post automatically — the mode word is the dashed-underline control that switches it) and one Turn on or Turn off button; "Pause all" under More; the trigger log behind a disclosure under the runs; the trigger switches on the workflow page. The workflow page: mode · version, then Starts when (one sentence), Checks (one line per read, or per step), Writes (the note's template quoted with `<device>` and `<time>`, or one line per step), the last five notes or runs, and Details (the full trigger rules with their switches, the approval rule, the approvers, the windows, the settings, the version). The run page: before approval, What will change as one line per step with the values behind each step's disclosure; approval as Who, How, Approve, with the time behind "Change time"; after it starts, Progress as a dot and a word per step with the plan behind "What was approved"; inputs, approval and undo as short lines in the rail. The report page: one table per device with the tickets behind a disclosure. The Notes view: one table (Workflow · Notes · Posted · Not useful · Faster to close?) with the weeks behind "By week". The words a screen shows are presentation: `NoteWorkflow.reads` and `.template` describe a note and may be reworded, while the text a workflow builds is pinned word for word in `tests/api/test_automation_notes.py` (`EXACT_NOTES`), so a wording change on screen cannot alter what is posted without a failing test.

## Automation: the library

A workflow is **data**: one YAML file in `app/automation/definitions/`, reviewed like code, assembled from **actions** in `app/automation/actions/`. `app/automation/library.py` loads, validates and compiles each file into the shapes the engine already runs (a `Workflow` of steps for a run; a `NoteWorkflow` for a note or a report), so nothing about the controls changed — only where a workflow comes from. `docs/automation-workflows.md` is the guide: how to write an action, how to write a definition with the device-online note as the worked example, validate and try. The rules:

- **An action is one small, tested block** (`actions/base.py`): a name and version, a plain-language title, typed inputs and outputs (`TYPES`: string, integer, number, boolean, list[string], ticket, device, read, note, facts), the connectors it uses, read or write, and for a write its exact **write scope**, which must be on `WRITE_SCOPES` — the allow-list of everything the engine may do to any system: *add internal ticket note*, and the practice table. Its functions are the contract the engine always had (precondition, plan, before, run, verify, undo), and its idempotency key names the inputs that with the run and the step make one act. The registry refuses a write with no verify, a scope off the list, an unknown connector or type; `tests/automation/test_actions.py` tests every action on its own against fixtures and runs each against a recording fake to prove it reaches only the connectors it declares. Reads go through the `Tools` protocol and writes through the `NoteWriter` the caller hands in; no action imports a connector, and the no-AI import guard covers `actions/` and `library.py`.
- **A definition cannot contain code.** A value is a literal or exactly one reference — `{inputs.x}`, `{steps.<id>.<output>}`, `{settings.x}`, `{ticket.x}` — and a string that looks like a reference and is not one is refused, so there is no way to write a template. A condition (`when`) is one reference and one operator (equals, not_equals, in, exists, greater_than, less_than) or a list of them; there are no loops, and an action that needs a list takes it as one input. The loader checks every reference against the declared types of what it names and refuses, in one line naming the file, the step and the problem: an unknown action, a missing or mistyped input, a reference to a step that has not run yet, a dependency cycle, a write without a verify, an undeclared setting, anything outside the syntax. `scripts/automation.py validate` runs the same checks, and the suite runs them (`tests/automation/test_library.py`).
- **A run records what it ran**: the definition's name, version and a SHA-256 of its **canonical form** (`library.canonical`: the parsed definition serialised one way — `automation_runs.definition_hash`, notes too, migration 0033), and each step row the inputs its references resolved to and the outputs the action returned, which the run page's Values show and later steps read. The hash is of the parsed definition and not of the file's bytes, because the same definition is not the same bytes on two machines (CRLF on a Windows checkout, LF on Render; a final newline, a byte order mark or trailing spaces an editor left), and a run's record of what it ran may not move for any of that; `.gitattributes` keeps the files LF everywhere as well, so a diff is a diff.
- **A workflow cannot be turned on for a client until its required settings are set.** A definition declares the settings it needs (type, default, required); `controls.set_switch` refuses (`NeedsSettings`) while one is missing, the Automations page shows "Needs settings" with the list behind it on the workflow page, and `manage_client.py report-config --automation-file` checks every value against the declared type and refuses a key no definition declares.
- **`try` before turning on.** `scripts/automation.py try <workflow> --client <slug> [--ticket <number>]` runs the workflow's dry run with real reads and no writes — a run workflow's preconditions and plans on a run that is never created, a note workflow's reads and note for one open ticket with the write step listed and never run — and prints what each step would do. It refuses on a client whose switch is on.
- **The existing workflows are definitions.** Practice (`practice.yaml`, from the four `practice.*` actions over the engine's own table; the functions are still `app/automation/practice.py`) and the six alert notes (`device_online`, `repeat_alert`, `disk_space`, `threat`, `backup_notice`, `chronic_devices`), each a chain of `devices.resolve`, the read actions gated by `when`, a `notes.*` action that holds the wording, and `autotask.add_note` as the one write (a report's single `reports.chronic_devices` step writes nothing). Everything they do is what it was: the pinned note text, the trigger tests, the engine tests and the page tests pass unchanged.

## Automation: alert notes

`app/automation/notes/` holds the first real workflows: when a monitoring alert raises a ticket, a note workflow reads the facts behind it from the tools and adds **one internal note** to the Autotask ticket. Nothing is closed, merged, reassigned or changed. `docs/automation-notes.md` is the operational page (the API user to request, the internal-only setting, the notification checks, the rollout); `docs/api-notes/autotask.md` has the vendor findings. The rules:

- **No AI, and fixed wording.** A note is a template in code filled with values read from tools, each value with the time it was read, and every body ends `Read by Desk at <time>`. The package imports no connector and no model (`tests/automation/test_imports.py` covers it); the live reads are injected as a `Tools` protocol whose one implementation is `app/tickets/alert_tools.py`, so the workflows are tested from fixtures, including a tool that does not answer and a device matched without confidence. A fact that cannot be read is one line saying which tool did not answer; a missing core fact (the device, the device's state, the ticket's own text for a backup notice) means no note, never a guess.
- **The only write is adding an internal note**, through `AutotaskNoteWriter` (`app/connectors/autotask/notes.py`): its own credential (`autotask_notes`, a second API user, never the read user), the reader's budget and backoff, and an allowlist of `GET`, `POST …/query` and `POST /V1.0/Tickets/{id}/Notes`; anything else raises `WriteNotAllowed` before a request. Titles start `Desk: `, and a title or body over the tenant's limit is refused, not truncated.
- **Internal only, read from the tenant's field information, never a number.** The writer reads the `TicketNotes` `publish` and `noteType` picklists from `entityInformation/fields` on the tenant it writes to and sends only the publish value labelled **Internal Project Team** — internal resources alone; `All Autotask Users` can be shown on the Client Access Portal and `Internal & Co-Managed` reaches the client's own technicians — and a note type among `Task Notes`, `Task Detail`, `Task Summary`, never one naming the client or the portal. A tenant without the internal-only label gets no note, and no wider audience is ever used instead. The request carries exactly `ticketID`, `title`, `description`, `noteType`, `publish`; the entity has no notification field, so whether a note notifies anybody is the tenant's workflow rules and note notification defaults, which `docs/automation-notes.md` says to check before any live post. `tests/connectors/test_autotask_notes.py` asserts the sent value against the field information and fails on any other; the demo's fake Autotask refuses any other value too.
- **Six workflows, alert rules on the new-ticket poll** — each a definition in `app/automation/definitions/`, its wording in `app/automation/actions/notes.py`. Device back online (NinjaOne state, last contact, last boot, open alerts); repeat alert on the same device (the device's tickets in 7 days, the device by the identity layer, no note unless confident; the alert *kind* is the title with the device's name taken out and then digits folded, so `CON-LT-044` is never a repeat of `CON-LT-043` and a machine named as its FQDN is the same machine); disk space (volumes, state, disk alerts in 30 days); antivirus/EDR threat (Bitdefender state and detections in 24 h; a Blackpoint note always ends "MDR alert: review required, do not close without investigation."); backup notices (the ticket's text parsed by fixed Veeam and N-able rules; an unknown format gets no note); chronic devices (every 30 days, a report page in Desk and no Autotask write). **At most one note per workflow per ticket**, kept by a unique index. Per-client values go under `automation.workflows.<name>` in settings.
- **Rollout is a mode per client per workflow** (`automation_note_modes`). **Preview** ("Review first" on screen), the default: the note is stored in our database and shown on the ticket page as a card — "Desk note" with a dot and a word, the note as it will appear in Autotask, Post to Autotask (the engineer's approval of that note) and Not useful, one line of workflow and time, the sources behind a closed disclosure. **Auto-post** ("Post automatically" on screen): every note is posted as built. Switching to auto needs the franchisee's approver recorded — name, method, time; on the client's approver list — and switching back is immediate; the rule for the mode in force is printed on the workflow page and under the note. The kill switch stops all posting in every mode. **Post and Not useful are Inputiv staff only** unless the client's `automation.notes.franchisee_can_post` (default false; `manage_client.py report-config --franchisee-can-post`) is on, when the franchisee's administrators and technicians may as well; off, a franchisee user is refused the note's JSON and sees no Desk note card, so whether a note exists is not something they are told until the franchisee has agreed to act on them.
- **Measured per note and per workflow.** Each note records built, posted (by whom, or auto), not useful, and when its ticket closed (`automation_alert_tickets`, filled by the poll); the Notes view on the Automations page gives, per workflow, notes built, the share posted in preview, the share not useful, and the median time to close with and without a note, per week. A workflow whose notes are mostly dismissed is switched off, not reworded on a guess.
- **Backfill and live go through the existing poll and its one switch.** `scripts/automation.py notes-backfill --client <slug> --dry-run` prints what the open alert queue would get and stores nothing; without `--dry-run` it builds preview notes only. The poll builds notes, posts in auto mode, builds due reports and records closures; all of it behind `AUTOMATION_TRIGGERS_LIVE`. No live Autotask write has been made yet: the writer is tested against mocks and the demo's fake, and the first live post is a recorded step in `docs/automation-notes.md`.

## Daily collector

`scripts/collect_events.py --client <slug>` (`app/events/collector.py`) reads one kind of vendor event for every active site with a mapping for the connector, once a day: today, Bitdefender detections. Each event is written to `collected_events` by its vendor id (`connector_name, kind, external_id` is unique), so a run repeated or overlapped duplicates nothing and a changed event is updated. Every window asked for is a `collection_coverage` row, `collected`, `failed` or `not_applicable` (the site cannot have the event kind: no EDR licence; a reader raises `NotApplicable`), so a report can tell a day nobody collected from a quiet day (`coverage_for` counts only `collected` windows). A site without the licence is never recorded as covered with zero events. A site that fails does not stop the run; each site's read is an `events_collected` audit row. A later connector adds a reader to `READERS` and nothing else. **Its Render cron is parked** (commented out by decision, 20 October 2026; `render.yaml`, docs/deploy.md §5), so it runs when somebody runs it. The block is complete and is `--all-clients` when enabled: every active client, oldest first, one after another, a client that fails reported with its slug and the run carrying on, the exit code saying whether any did. It is the only thing that recomputes a client's day, so while the cron is parked a coverage board is written when somebody presses Refresh or runs the collector by hand, and at no other time. That is why the board prints how old it is. After the events the run fills the outcome ledger for the last `--outcome-days` days (`--no-outcomes`; see "Resolved: clocks, ledger, baselines"), resolves device identities (`--no-devices`), takes the day's coverage snapshot (`--no-coverage`) and then stores the day's agreement between the join and the links, in that order, so the snapshot, the links and the comparison are as of the same inventories.

## Testing and quality

- `pytest` must pass before any commit. Run `ruff check` and `ruff format`.
- New connectors are not "done" until fixtures exist and a human has validated at least one live call against the real console.
- Do not write tests that call real APIs. Live validation is a manual step recorded in `docs/validation-log.md`.

## Working conventions

- Small commits with descriptive messages. One connector or one feature per PR.
- When a vendor API is ambiguous or undocumented, write what you found in `docs/api-notes/<vendor>.md` rather than guessing in code.
- **At most one live run per task, on a single site where the question allows, and iterate against fixtures.** A live run is the check at the end, not the loop in the middle: the recorded inventories and `tests/coverage/test_agreement.py` are where a matching rule is tried and retried, and a vendor's slowness or a timeout on a live day is a finding to record, not a reason to run again. 2026-09-28 spent five tenant-wide live runs on one task while GravityZone was slow; one, for `austin-tax-advisors`, would have answered the question.
- **A live probe prints counts, ids, keys, types and enums, and never a name.** No customer, site, device, user, contact or company name goes to the terminal, a log, a commit message or a scratch file that outlives the probe: print `rows=94`, `grades={B: 32, E: 32}`, `asset 1001`, never what the machine is called. The same goes for a name passed *into* a probe as an argument, which lands in the shell history and the process list: look the record up by id, or read the name from a file the probe itself reads. Recorded responses are scrubbed before they become fixtures, and a slip is recorded in the validation log.
- If a task would take more than the planned scope (see build order), stop and summarise the options.
- Ask before adding a dependency not listed in the stack.
- **A new sub-config on `FranchiseeConfig` may not reach a connector at import
  time.** `app/connectors/__init__.py` imports the Autotask tools, which read
  the settings, so anything `app/reports/tbr/config.py` imports that touches
  `app.connectors` is a circular import — and it surfaces as a confusing
  `partially initialized module` on an unrelated module, not where the import
  was added. `BackupConfig` lives in `app/reports/tbr/backup_config.py` for
  that reason, importing the one connector function it needs inside the method
  that uses it. The same applies to the next one.

## Out of scope until told otherwise

- **Splitting `Device.os` into an OS family and an OS name.** It holds both
  today, depending on which connector wrote the row: a family (`Windows`) for
  a machine NinjaOne found, because the org-scoped device listing carries no OS
  string, and a real OS name for one Bitdefender or ConnectSecure wrote. That
  ambiguity put every Windows server through `device_role` as a workstation —
  `"windows"` without `"windows server"` — so a server at a servers-only site
  read "not in backup scope", which is the opposite of right about the machine
  whose missing backup matters most. The stopgap is that **nothing passes
  `Device.os` to `device_role`**: the node class decides, as the board's does.
  The fix is two columns, `os_family` and `os_name`, the second filled from
  NinjaOne's `operating-systems` query — the read the review's collector
  already makes and the daily resolution does not. Until then the one case
  `device_role` exists for (a Windows 10 IoT till classed `WINDOWS_SERVER`) is
  decided correctly only in the review.

- **A CSV export on the ticket queue.** Coverage and Devices both have one
  and the queue does not: `/tickets/list` has no export route, so the page
  offers none rather than a button that downloads what is on screen, which
  would be a different population from the filters a reader had set.

- Any write action to external systems. When it comes, it comes through the automation engine and nowhere else (hard rule 2).
- Anonymised cross-MSP data sharing.
- Microsoft Entra single sign-on. The user model is shaped for a per-organisation provider (`identity_provider`, `external_subject`) and nothing else is built. Not to be confused with the Microsoft 365 connector, which *reads* a customer's directory and has nothing to do with how anybody signs in to Desk.
- An Exchange Online connector. What it would need — `Exchange.ManageAsApp`, a certificate, a directory role and a PowerShell runtime — and what it would add is written down in `docs/m365-connector.md`.
- Sharing a conversation thread between people.
- ConnectWise or Datto RMM connectors (Phase 2).
- Autonomous remediation of any kind.
